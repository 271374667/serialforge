# 接收定界与编码

> 串口线只会吐出一连串没有感情的字节流。所谓的“句号”，全凭上位机和下位机之间的默契。

在串口通信中，最容易引起混淆的是这两件事：
- **发送终止符（Terminator）**：我给设备写信，信纸末尾盖什么戳（通常是 `\r\n`）。
- **接收定界（Framing）**：设备给我回信，我怎么知道它一句话什么时候算说完了。

这两件事在物理上是完全独立的。发信带回车换行，并不代表设备回话也会乖乖带换行。

---

## 四种常见的断句策略

SerialForge 将断句的规矩统一收在 `FramingConfig` 里：

| 定界模式 | 它的工作原理 | 形象比喻 | 适用设备类型 |
| --- | --- | --- | --- |
| **`LINE`（默认）** | 只要遇到指定的换行符（如 `\r\n`）就切出一帧 | 说话带句号 | 绝大多数遵循 ASCII 协议的智能仪表与开发板 |
| **`SILENCE_GAP`** | 线路连续沉默超过指定时间，就算一句话结束 | 对方停顿喝口水，默认话讲完了 | 很多老旧温湿度传感器、部分类 Modbus 协议 |
| **`DELIMITED`** | 遇到特定的字节分隔符（如分号 `;` 或 `\x00`）就切分 | 用分号串起一整串话 | 某些自定义二进制或单字符间隔协议 |
| **`LENGTH_PREFIX`** | 报文开头先报长度，读够字数自动收帧 | 快递单上明确标着“内含 32 字节” | 高性能高密度的自定义二进制规约 |

## 解决老大难：没有换行符的设备怎么破？（SILENCE_GAP）

很多工业传感器为了追求极限效率，发出来的报文根本不带 `\r\n`。它一口气吐出 8 个字节的十六进制数据，然后就陷入了漫长的沉默。

如果你用普通的串口助手或行模式去读，程序会永远在那儿苦等换行符，最后怒甩一个超时错误。

使用静默定界轻松化解：

```python
from serialforge.advanced import FramingConfig, FramingMode

# 配置为静默定界：如果线路上持续 80 毫秒没有新字节到来，说明这一包发完了
forge.configure(
    baudrates=[9600],
    probe=PING,
    framing=FramingConfig(
        mode=FramingMode.SILENCE_GAP,
        silence_gap_s=0.08,  # 80 毫秒静默停顿
    ),
)
```
底层读取线程会在检测到线路安静超过设定阈值后，自动把积攒的字节打包并推进解析流水线。

## 字符编码：GBK 与 UTF-8

`encoding` 控制文本协议的编码方式，库默认使用 `utf-8`。

如果你的设备是国内传统厂家生产的，屏幕上经常回显中文（比如 `报警: 电机过热`），在 `utf-8` 下可能会变成一串满屏乱码（形如 `\xe6\x8a\xa5\xe8\xad\xa6`）。

直接在配置中修改编码：

```python
forge.configure(
    baudrates=[115200],
    probe=PING,
    encoding="gbk",  # 适配国内老旧设备的 GBK/GB2312 编码
)
```

## 物理回显过滤（`echo=True`）

有些设备或者 RS-485 硬件总线有个“讨人嫌”的毛病：你发出去的指令，硬件线路会像回音壁一样，先把你的指令原封不动弹回来，紧接着才是它的真实回复。

如果不开启回显过滤，上位机会误以为自己说的话就是设备回包，导致解析结果一团糟。

只要在配置中声明 `echo=True`：

```python
forge.configure(
    baudrates=[115200],
    probe=PING,
    echo=True,  # 自动吃掉物理回显，只留真正的响应报文
)
```
SerialForge 在匹配命令前会自动帮你筛除物理回音，保护上层逻辑的干净。
