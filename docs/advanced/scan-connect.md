# 扫描与连接

> 扫描设备的过程，就像在一整栋黑漆漆的宿舍楼里挨个敲门问：“同学，请问你是会回 PONG 的那位吗？”

上位机软件最常见的一个槽点就是：每次换个 USB 口插设备，Windows 分配的 COM 编号就从 `COM3` 变成了 `COM7`。如果是做商业软件或者给非技术人员用的测试工具，让用户去设备管理器里肉眼翻找 COM 口，体验可谓灾难。

让程序自己找设备才是正道。但如果你自己写扫描，通常会掉进这两个大坑：
1. **死等慢如蜗牛**：把 `COM1` 到 `COM20` 串行轮询一遍，每个口等 1 秒，一轮下来 20 秒过去了，用户以为软件卡死了。
2. **碰上“流氓串口”当场暴毙**：某些蓝牙虚拟串口或质量堪忧的转接芯片，一旦调用 `open()`，整个线程直接被操作系统驱动锁死，拉都拉不回来。

SerialForge 的扫描引擎专门针对这些毛病做了工程加固。

---

## 推荐的标准扫描姿势

直接使用 `scan_async()`，它自带完整参数配置，在后台辅助线程里并发探路，搜寻完毕后通过主线程闭包送上候选设备列表：

```python
# 1. 声明探针（拿它去敲门）
PROBE = forge.add("PING", r"PONG")

# 2. 回调函数：当发现设备后，自动发起连接
def on_devices_found(devices: list[DeviceInfo]) -> None:
    if not devices:
        self.status.setText("没找到任何匹配的设备")
        return
    
    target = devices[0]
    self.status.setText(f"找到设备 {target.port_name}，正在连接...")
    
    # 直接使用 DeviceInfo 连接，秒连！跳过二次探测
    forge.connect_async(target).add_done_callback(on_connected)

def on_connected(device: DeviceInfo) -> None:
    self.status.setText(f"连接成功: {device.port_name} @ {device.baudrate}")
    # 此时已经可以愉快地发送业务指令了

# 3. 触发异步扫描
call = forge.scan_async(
    baudrates=[115200, 921600],
    probe=PROBE,
    vid_pid=[(0x1A86, 0x7523)],  # 可选但极度推荐：只探测 CH340 芯片的端口
)
call.add_done_callback(on_devices_found)
```

---

## 三个关键参数的门道

### 1. `baudrates`（候选波特率列表）
设备的语速可能被设置成了 `115200`，也可能是 `9600`。你可以传入一个列表，库会按顺序尝试。

这里有个底层性能优化：**同一端口只打开一次物理句柄**，然后在同一个句柄上快速切换波特率，避免了频繁打开/关闭串口带来的巨大操作系统开销。

### 2. `probe`（探针）
探针就是你敲门时喊的暗号。
- 必须是单发单收（`SINGLE`）且不带动态占位符的命令。
- **探针的正则表达式绝不能匹配它发出去的请求文本**。比如发 `PING`，正则如果写成了太宽泛的 `P.*`，库会将其判定为“设备正在把我的话原样复读回来”（回显），从而直接抛出 `ConfigError` 阻止你埋雷。

### 3. `vid_pid`（USB 身份标识，加速神器）
这是解决“扫描慢”的终极杀招。

USB 转串口芯片都有固定的厂商 ID（VID）和产品 ID（PID）。例如国民级芯片 CH340 的 VID/PID 是 `(0x1A86, 0x7523)`，FTDI FT232 是 `(0x0403, 0x6001)`。

- **省略 `vid_pid`**：库会去敲电脑上每一个 COM 口的门（包括主板自带串口和蓝牙虚拟口）。
- **提供 `vid_pid`**：在尝试打开串口之前，库会先盘查 USB 设备清单。不在名单里的端口**直接跳过，连碰都不碰**。

在一台插了蓝牙模块或者各种工业总线适配器的工程电脑上，这一项能让原本需要 5 秒的扫描直接压缩到 50 毫秒。

## 探测速度与防护机制

为什么 SerialForge 的扫描又快又稳？因为它内建了三道防护：

1. **防假死超时（`probe_open_timeout_s`，默认 1.0 秒）**：
   打开端口的操作被放在一个可主动放弃的辅助线程中。一旦碰上损坏的驱动让 `open()` 无限卡死，库在 1 秒后会直接抛弃这个残废句柄并转向下一个端口，绝不让一个坏端口拖垮整场扫描。
2. **字节活性窗口（`probe_activity_window_s`，默认 0.3 秒）**：
   敲门之后，先在 0.3 秒内静听“线路有没有任何回包字节”。如果一丁点动静都没有，果断切换到下一个波特率，不用傻等满 1 秒的协议超时。
3. **逐端口容错，拒绝全盘崩溃**：
   如果某个端口因为被其他软件占用（Access Denied）、写入失败或校验不通过，库只会默默跳过该端口。如果整台电脑一台匹配的设备都没有，返回的只是一个干净的空列表 `[]`，绝不会用大段内部异常惊吓调用方。

---

## 两种扫描模式：全部找齐 vs 先到先得

通过 `mode` 参数控制：

- **`ScanMode.ALL`（默认）**：把所有候选端口完整扫一遍，返回所有能答上暗号的设备列表。适合有多台相同设备需要用户在下拉框挑选的场景。
- **`ScanMode.FIRST_MATCH`**：只要任何一个端口成功回对了暗号，立刻协作取消其余所有正在进行的并发探测，以最快速度交卷。适合现场只有一台主控制器的场景。

## 连接的三种姿势

```python
# 姿势 1：最推荐！传入扫描得到的 DeviceInfo，秒级直连，不走二次探测
forge.connect_async(devices[0])

# 姿势 2：明确指定端口号，跳过 USB 身份过滤，但仍然会自动探测波特率
forge.connect_async("COM3")

# 姿势 3：无参调用，按照上一次 configure() 保存的策略自动寻找首个可用设备
forge.connect_async()
```

每次调用 `scan_async()` 或 `connect_async()`，库内部都会**先彻底断开旧的会话并回收资源**。即使你对同一个已连接的设备再次调用连接，它也会干净利落地走完一次完整的重新初始化，绝不留下陈旧状态污染新会话。
