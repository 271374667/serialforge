# 术语表

这页是“看不懂就跳过来”的地方。正文里第一次出现的硬件、协议和库内名词，大部分都能在
这里找到一句人话解释。不需要从头背，遇到再查。

如果你连“串口到底在传什么”都还没概念，先看[串口与上位机入门](serial-primer.md)，
那张地图比逐条查词更容易建立整体印象。

## 串口与硬件 {: #serial-basics }

### 串口 / COM 口 {: #serial-port }

电脑和外部设备之间的一条“窄窄的对话通道”。在 Windows 的设备管理器里，它通常长成
`COM3`、`COM11` 这样。你可以把它想成一根只能排队的单车道：字节一个接一个过去，不会
因为你是 GUI 就给你让路。

物理上它可能是 USB 转串口芯片（CH340、CP210x、FT232 等）虚拟出来的，也可能是主板上
真正的九针串口。对程序来说都一样：打开一个 `COMx`，读字节，写字节。

### 上位机 {: #host }

坐在你这边、运行 Qt 程序的那台电脑。它负责发命令、收数据、画界面，通常比设备“话多”。
对应的下位机就是设备侧的单片机或控制板。

### 下位机 / 设备 {: #device }

真正干活的那块板子。它可能只会几种固定句式，比如收到 `PING` 回 `PONG`，收到
`ReadAll` 吐三行数据。它没有你的界面那么聪明，也不会读心术，所以协议要写清楚。

### UART / USB-CDC {: #uart }

UART 是芯片之间常见的串行通信硬件；USB-CDC 是让 USB 设备“伪装成串口”的标准。
无论哪一种，Windows 最终都会给你一个 `COMx`，上位机代码不用为它们写两套。

### 波特率 {: #baudrate }

双方说话的“语速”，单位是 bit/s。常见值有 `9600`、`115200`、`921600`。两边语速不
一致，收到的就是一堆乱码或干脆没有回应。串口调试里最常见的翻车现场，就是设备在
`115200`，上位机却在 `9600` 深情呼唤。

serialforge 扫描时会逐个尝试候选波特率，省得你手动一个个试。

### VID / PID {: #vid-pid }

USB 设备的“厂牌”和“型号”编号。VID 是厂商编号，PID 是产品编号，合起来能大致认出
“这是不是我要找的那类设备”。它不能保证每台设备唯一，但用来在扫描前过滤掉大量无关
串口非常有效。

### 8N1 {: #8n1 }

串口最常见的帧格式：8 个数据位、无校验（None）、1 个停止位。绝大多数设备默认就是
8N1，serialforge 的 `SerialConfig` 默认也是 8N1、无流控。

### 流控 / DTR / RTS {: #flow-control }

流控是“你先别发，我这边缓冲要满了”的握手机制，常见有 RTS/CTS 和 XON/XOFF。
DTR、RTS 是串口上的两根控制线，有些设备靠它们复位或进入下载模式。

serialforge 默认不碰这些线；需要时用 `SerialConfig` 显式设置，避免“打开串口顺便把
设备复位了”的惊喜。

## 数据与协议 {: #protocol-basics }

### 字节与十六进制 {: #bytes-hex }

串口传的是字节。`b"PONG\r\n"` 前面的 `b` 表示 bytes；日志里常见的 `50 4F 4E 47`
是同样四个字节的十六进制写法。看到 `\r\n` 就是回车加换行，很多设备拿它当一句话的
句号。

### 帧与定界 {: #frame }

“帧”就是协议里一次完整的信息。问题是串口是流式的：字节像水一样连续过来，程序怎么知道
哪几个字节算一帧？这就需要“定界”。

常见定界方式：

- 按结束符断句（`LINE`，比如 `\r\n`）；
- 两帧之间安静一段时间（`SILENCE_GAP`）；
- 用特殊分隔符（`DELIMITED`）；
- 开头先报长度（`LENGTH_PREFIX`）。

serialforge 把这些策略收在 `FramingConfig` 里。

### 结束符 / CRLF {: #terminator }

`\r\n` 就是 CRLF（回车 + 换行）。很多设备只认带结束符的请求，就像寄信要贴邮票。
serialforge 默认发送时补 `\r\n`，你声明请求文本时不用自己写。

### 回显 {: #echo }

有些设备会把收到的请求原样再发回来，叫回显。对程序来说，这回显很容易被误认成回复。
`echo=True` 会让库先把回显过滤掉，再匹配真正的响应。

### 探针 {: #probe }

扫描设备时用来“敲敲门”的那条命令。比如发 `PING`，能收到 `PONG` 就说明这个端口后面
大概率是目标设备。探针要短、要稳，最好不会改变设备状态。

### TX-RX 回环 {: #loopback }

把一根线一头接 TX、另一头接 RX，让设备发出去的字自己收回来，用来验证串口通路。
测试时要接独立适配器；接到目标设备上，它通常不会配合你回显
`SERIALFORGE_LOOPBACK`。

### 校验和 {: #checksum }

有些协议会在帧尾带一个校验值，用来发现传输过程中的位翻转。serialforge 不替你实现
业务校验；需要时在 `parser` 里自己算，或者在声明里用 `error_pattern` 识别设备回的错误帧。

### 正则表达式 / 命名组 {: #regex }

正则就是“用一张模式纸条去比对文本”。`\d+` 表示一串数字，`.*` 表示任意内容，
`(?P<value>\d+)` 是命名组：匹配到的数字会以 `value` 为名交给你，省得再按下标猜。
serialforge 用正则匹配整帧响应，命名组可以直接变成 `dict` 或 dataclass。

### RX / TX {: #rx-tx }

RX 是接收（receive），TX 是发送（transmit）。日志里看到 RX 就是“设备说”，TX 就是
“我们发”。这两个缩写不神秘，只是工程师为了少写几个字母。

### 独占命令 / EXCLUSIVE / BUSY {: #exclusive }

独占命令就是“这条命令执行期间，别的普通命令先靠边”。设备只有一张嘴，一问一答的
命令同时挤进去会串台。流式采集期间再发独占命令，库会返回 `BUSY`，意思是“后厨这口锅
正占着，你等会儿”。

### TAGGED {: #tagged }

带标签的请求：设备会在回复里带回请求里的标签，方便在流式输出中认出“这是对我上一条
命令的回复”。它适合在设备持续吐数据时插一句状态查询。

### 退避 {: #backoff }

重连不会每秒猛敲一次门。失败后先等一会儿，再等久一点，避免把设备和驱动逼疯；
这个“越等越久”的策略就叫退避。

## 软件与线程 {: #software-basics }

### 事件循环 {: #event-loop }

Qt 的“前台接待”：不断从队列里取事件（点击、定时器、信号）并处理。`app.exec()` 一跑，
接待员就上班了。如果你在槽函数里阻塞太久，接待员就去喝茶了，界面会卡。

### 主线程 / 工作线程 {: #threads }

主线程通常就是 GUI 线程，负责画界面；工作线程负责耗时或会阻塞的 I/O。serialforge
把串口读写放在自己的工作线程里，再把结果排队回主线程，所以你可以在回调里直接改控件。

### I/O 线程 {: #io-thread }

专门负责读写串口的后台线程。它不怕等，怕的是主线程陪它一起等——主线程一卡，界面就
变灰，用户就开始点“关闭程序”。serialforge 的 I/O 线程由库管理，退出时用
`disconnect()` 把它好好送走。

### aboutToQuit {: #about-to-quit }

Qt 应用退出前发出的信号。把 `forge.disconnect()` 接上去，相当于打烊前关灯，避免
解释器结束时 I/O 线程还在后台游荡。

### loguru {: #loguru }

一个 Python 日志库，serialforge 内部用它写 DEBUG 日志。默认是静默的，不会突然在你
控制台刷屏；要排查问题时再通过 `LogConfig` 打开文件日志。

### pyserial {: #pyserial }

Python 里操作串口的底层库，serialforge 用它打开 `COMx`、读写字节。你通常不需要直接
调用它；把它想成“库的库”就行。

### 编码 / UTF-8 / GBK {: #encoding }

字节和文字之间的翻译规则。同一串字节按 UTF-8 解码是中文，按 GBK 解码可能就成了乱码。
设备用哪种编码，`DeviceProfile.encoding` 就填哪种；不知道就先用默认的 UTF-8 试。

### dataclass {: #dataclass }

Python 自带的数据类写法，用字段名描述一个对象。serialforge 支持把命名组直接构造成
dataclass，这样 `message.data[0].version` 比 `message.data[0]["version"]` 更适合
让 IDE 补全，也更不容易拼错字段。

### 阻塞 / 非阻塞 {: #blocking }

阻塞就是“我在这里等到有结果再走”，非阻塞就是“我先去忙别的，好了叫我”。`scan_sync`
和 `send_sync` 是阻塞的，适合脚本和后台线程；`*_async` 是非阻塞的，适合 GUI。

### 回调 / 闭包 {: #callback }

回调是“事情办完后要调用的函数”。闭包是“顺手把周围变量一起打包带走的函数”。Qt 里常见
的写法：

```python
def on_done(message):
    self.label.setText(str(message.data[0]))
```

这个 `on_done` 捕获了 `self`，所以它知道该更新哪个控件。serialforge 会把这个闭包排队
到主线程再执行，不需要你手动 `QMetaObject.invokeMethod`。

### 信号槽 {: #signal-slot }

Qt 的发布订阅机制：信号发出，槽函数被调用。serialforge 的 `connection_state_changed`、
`received`、`raw_sent` 都是信号；连接它们就是“订阅这些事件”。

### 队列与优先级 {: #queue }

命令得排队，不能想插队就插队。serialforge 内部有一个队列，默认先来先发；`URGENT`
优先级可以理解为“这张单子先处理”。流式采集期间，普通独占命令会被判 `BUSY`，因为
设备只有一张嘴。

### 超时与期限 {: #timeout }

超时是“最多等多久”。serialforge 有两层：声明里的协议预算（等设备回一帧）和调用期限
（从提交到结果送达主线程）。默认 3 秒量的是调用期限，设备响应只是其中一段，别把两者
混为一谈。

### 幂等 {: #idempotent }

同一个操作做一次和做多次，效果一样。`add(SPEC)` 重复添加同一个声明对象是幂等的，
不会注册出两条命令。

### 冻结 / 不可变 {: #frozen }

对象创建后字段不能改。`Spec` 和 `Message` 都是冻结对象，好处是你不用担心中间被谁
偷偷改了字段；声明对象也因此可以安全地跨线程、跨回调复用。

## serialforge 词表 {: #serialforge-terms }

### 门面 {: #facade }

一个把复杂子系统包起来的“前台”。你只跟 `SerialForge` 打交道，不用自己拼串口、
调度器、探测器和日志组件；它们在里面怎么协作，是库的事。

### Spec / 声明 {: #spec }

一条命令或事件的“说明书”：请求文本、匹配规则、返回类型、响应模式。声明一次，之后
一直用同一个对象发送。库不复制它，所以回调里可以用 `message.spec is SPEC` 认领结果。

### 调用句柄 {: #call-handle }

`send_async` / `scan_async` / `connect_async` 返回的那个对象，像取餐号。你可以查
`done`、读 `result()`、注册回调，或者 `cancel()`。句柄在，结果就找得到。

### 快照 {: #snapshot }

某一刻的数据副本。`context` 是只读浅快照：你在里面放 `{"row": 7}`，回调收到的还是
这份内容，不会被别的调用串改。

### Message {: #message }

一次接收或一次调用的“信封”：里面装着解析后的 `data`、原始帧、所属声明、调用 ID、
上下文和状态。`Message.data` 永远是列表，单条响应也是单元素列表。

### params / context {: #params-context }

`params` 用来填请求里的占位符，比如 `Read {channel}` 里的 `channel`；它会被发到设备。
`context` 是给自己看的便签，比如 `{"row": 7}`，不会上线，也不会参与匹配。

### received / raw_sent {: #signals }

`received` 只发非空的原始接收字节，适合做滚动日志；解析后的结果从调用句柄或回调取。
`raw_sent` 是实际写进串口的字节，适合排查“到底发出去了什么”。

### 扫描 / 连接 {: #scan-connect }

扫描是“挨个端口敲门，看谁答应”；连接是“选定一个端口，正式建立会话”。扫描不会自动
连接，连接前会先清理旧会话。

### SINGLE / MULTI / STREAM / NO_REPLY {: #response-modes }

- `SINGLE`：一问一答；
- `MULTI`：一问多答，靠数量或结束标记收尾；
- `STREAM`：设备持续输出，直到你叫停；
- `NO_REPLY`：只管发，不等回复。

主动上报则是“设备主动开口”，用只带 `pattern` 的事件声明接住。

### 心跳 / 重连 {: #heartbeat }

心跳是隔一段时间发个小探针，确认设备还在；重连是掉线后按退避策略自动重新打开串口。
`heartbeat_s=-1.0` 可以关掉心跳，适合那些“多问一句就重启”的敏感设备。

## 还是没找到？ {: #missing }

在 [Issues](https://github.com/271374667/serialforge/issues) 里描述你遇到的现象：设备型号、
波特率、发出的字节、收到的字节。带上 `raw_sent` 和 `received` 的原始数据，通常比
“它没反应”更容易定位问题。
