# 03 · 架构与扩展规则

新增模块、调整目录结构、跨层调用、重构前读本文件。

## 1. 分层与依赖方向

统一采用**单向依赖**，箭头只能从上往下，禁止反向依赖和跨层直连：

```
入口层 (cli / app / main)
    ↓
应用层 (use case / service：编排业务流)
    ↓
领域层 (domain / core：纯业务规则，不依赖外部世界)
    ↓
基础设施层 (infra：IO、数据库、网络、文件系统、第三方 SDK)
```

- **领域层不许** import 基础设施层（不碰 IO、不读环境变量、不调用 SDK）。
  需要外部能力时，在领域层定义抽象接口（ABC / Protocol），由基础设施层实现，在入口层注入。
- **上层可以**调用下层，**下层绝不**回调上层（需要通知时用回调/事件接口，同样由上层注入）。
- **禁止同级之间传递调用**：同一个 `service` 不许调用另一个 `service` 的方法。
  正确做法是由**更顶层**的模块同时编排这两个同级模块——横向协作的责任永远上移一层，
  不在层内互相拉扯。
- **禁止跨越多个层级跳级调用**：一个模块正常情况下只能调用**比它层级低的模块**，
  不要为了方便越过中间层直接 deep-dive 到底层的某个子目录模块。
- **全局例外**：真正全局、所有层都可见的内容不受上述限制——
  如 `src/core` 里的全局共享对象/常量、`src/utils` 里的全局工具类。
  例外只限"无业务状态的全局内容"，业务逻辑之间的调用关系仍必须逐层走。

## 2. 目录约定

```
src/<package>/
├── __init__.py
├── cli.py            # 命令行入口（可有可无）
├── config.py         # 配置对象与加载
├── domain/           # 领域模型与规则（纯逻辑，易测）
├── services/         # 用例编排
├── infra/            # 外部世界适配：文件、网络、DB、第三方 SDK
└── utils/            # 无业务含义的通用工具（保持很小）
```

- 新代码**先问属于哪一层**，再决定放哪个目录；放错层比命名难看严重得多。
- 一个目录文件数超过 ~12 个，按业务概念再切子目录，而不是继续堆。

## 3. 扩展方式（加新功能时）

按下面顺序思考，不要一上来就改现有类：

1. **能不能加一个类？** 新行为 = 新实现 + 注册到工厂/注册表，避免改老代码。
2. **能不能加一个参数？** 而不是复制一份函数改两行。
3. **确实要改现有类时**：先确认它的公开契约（docstring 描述的语义），
   保持向后兼容；不兼容的改动必须先说明影响面。

**开闭原则的具体做法**：

- 可替换实现 → 定义 `Protocol` / `ABC` + 注册表字典 `{"json": JsonParser, "yaml": YamlParser}`。
- 可配置项 → 收敛进一个 dataclass 配置对象，而不是散落的参数链。
- 可选行为 → 用策略对象 / 钩子，而不是在方法里堆 `if`。
- **新增行为 = 加新类 + 注册，不修改已有类**；发现自己在往老方法里塞 `if isinstance(...)`
  分支时，停下——那是该抽策略/多态的信号。

**里氏替换原则的具体做法**：

- 子类必须能无感替换父类出现的任何位置：不强化前置条件（父类接受的输入子类也必须接受）、
  不弱化后置条件（父类承诺的输出子类至少同样兑现）、不抛出父类声明之外的新异常。
- 子类**不要**重写父类方法后"掏空"其语义（空实现 / 抛 `NotImplementedError` 是坏味道），
  该拆接口就拆接口，不要逼子类继承用不到的方法。

**静态分发的具体做法**（配合 `rules/02` §3）：

- 按类型/名称分发用**提前定义好的映射表**（字典 → 已定义的类或方法），不用 `hasattr`
  探测、不用 `getattr(obj, name)` 动态拼接调用、不运行时增删属性与方法。
- 新增一种分发分支 = 在映射表里注册一个已定义好的类，编译期/静态检查期就能发现拼写错误。

## 4. 重构纪律

- **重构与功能修改分开提交**：先提交"纯重构，行为不变"，再提交"功能改动"。
  出问题时可以干净回退（配合 `05_git_and_commits.md` 的节点提交）。
- 重构前确认现有行为有测试覆盖；没有 → **先补测试**，再重构。
- 禁止"顺便"重构：本次任务无关的代码不要动，确有改进点记入 `.agents/docs/todo/`。
- 大型重构必须建 checkpoint，每完成一个可编译/可测试的子步骤就 commit。

## 5. 接口设计

- 公开 API 参数 **<= 5 个**，超过则收敛为配置对象。
- 返回值语义单一：不要"返回 dict 表示成功、抛异常表示失败"这种混搭。
- 跨模块传递的数据用 `dataclass` / `TypedDict` 定义清楚，**不传裸 dict**。
- 函数的副作用要显式：名字里体现（`save_*` / `send_*`），纯查询不要有副作用。

## 6. 配置与常量

- 配置来源优先级：默认常量 < 配置文件 < 环境变量 < 命令行参数。
- 配置集中在一个模块解析成对象后注入，**不要在业务代码里到处 `os.getenv`**。
- 魔法数字必须提取为具名常量并注明单位（`TIMEOUT_SEC = 30`）。

## 7. 架构决策记录

凡是**非直觉的架构选择**（为什么自己写而不用库、为什么拆成两个服务、
为什么用这种数据结构），必须在以下两处同时留痕：

1. 代码里用 docstring 的 `Note:` 简短说明；
2. `.agents/docs/knowledge/software/` 下写一篇 `NNNN_*.md`，写清背景、备选方案、选择理由。

否则下一次会话（另一个 AI）会把它当成"随手写的"而改掉。
