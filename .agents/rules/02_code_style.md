# 02 · 编码规范

编写或修改任何代码前读本文件。

## 1. 五条铁律

1. **按职责组织**：用类封装状态与资源，纯计算使用函数，设计模式按实际复杂度选用。
2. **允许顶层函数**：纯函数、pytest fixture、测试函数、CLI 入口和框架回调无需套静态方法类。
3. **模块公开 API**：显式定义稳定接口，不要求每个模块都有同名入口类。
4. **静态性**：像写 Java 这类编译型语言一样写 Python——变量的类型一经确定不可变更，
   属性与方法在类定义时**全部提前声明**，禁止运行时动态增删（详见 §3）。
5. **完整类型注解**：所有函数、方法、类属性都必须有类型注解（参数 + 返回值），**没有例外**。
   另加 Google 风格文档字符串：模块、类、公开方法必写 docstring。

## 2. 面向对象

### 模块组织（不可协商）

- 模块顶层可定义函数、类和常量，避免导入时执行有副作用的业务操作。
- 无状态工具直接使用函数；有状态或需要释放资源的对象使用类。
- 公开 API 可以是函数或类，不强制通过门面类转发。
- **多使用设计模式**：可替换行为用策略 + 工厂，对象创建复杂用建造者，通知/回调用观察者，
  流程固定步骤可变细节用模板方法。选最简单够用的那个，不为模式而模式。
- **禁止上帝类**：一个类的公开方法超过 ~10 个，或需要"和/或/然后"才能描述它的职责时，拆。
- **禁止超大文件**：单个 `.py` **硬上限 3000 行**，超过必须拆分（通常 ~500 行就该考虑拆了，见 §9）。
  拆分时保留清晰的公开接口。

### 设计取向

- **组合优于继承**；继承只用于真正的 is-a 关系，且层级不超过 2 层。
- **依赖注入**：类需要的外部资源通过构造函数传入，不要在类内部 `new` / 全局单例。
- **小接口**：公开方法签名保持精简，参数超过 5 个 → 收敛为配置对象 / dataclass。
- **不变性优先**：能用 `dataclass(frozen=True)` / 只读属性就用，减少隐蔽的状态变更。

## 3. 静态性纪律（像编译型语言一样写 Python）

业务代码优先显式字段与可检查的接口；框架适配、序列化边界和测试替身可按需使用动态能力，
将其限制在小范围并补充验证。以下为普通业务代码的默认约束：

| 禁止 | 替代方案 |
| --- | --- |
| `hasattr(obj, "x")` 探测属性 | 属性在类定义时声明齐全，用 `None` 默认值 + 显式判断 `if obj.x is not None` |
| `getattr(obj, name)` / `setattr(obj, name, v)` / `delattr` | 提前定义好属性与方法；按名分发用字典映射到**已定义**的方法 |
| 运行时给实例/类临时增删属性或方法 | 所有属性、方法在 `class` 定义里写全 |
| 一个变量的类型中途改变（`x: int` 后赋 `str`） | 类型一经声明不变；需要多种形态 → 定义继承体系或用明确的联合类型并全程一致 |
| `__dict__` / `__slots__` 玩花样、动态 `__getattr__` 分发 | 显式写出全部字段与方法 |

- **宁可多写代码也要静态**：重复一点样板（显式的方法分发字典、显式的字段声明）可以接受，
  换来的是 IDE / 类型检查器能全量检查、AI 接手时看得懂全貌。
- 所有属性在 `__init__`（或类体）中初始化并注解类型，即使初始值是 `None` 也要显式声明。
- 配合项目已选类型检查器（新项目首选 ty，见 `06_python_toolchain.md`）：
  动态增删属性、类型变更都会被拦下；大任务收尾跑 `uv run ty check` 必须通过
  （中间提交不跑，见 `06_python_toolchain.md` §4）。
- 面向对象设计原则的底线：**开闭原则**（扩展加新类，不改老代码）与
  **里氏替换原则**（任何子类对象必须能无感替换其父类出现的位置，不得强化前置条件、
  不得弱化后置条件）——细则见 `rules/03` §3。

## 4. 类型注解

```python
from pathlib import Path
from collections.abc import Sequence, Iterator
from typing import Optional

# ✅ 完整注解
def load_config(path: Path, *, strict: bool = True) -> dict[str, object]: ...

# ✅ 可为 None 显式标注
def find_user(uid: int) -> Optional["User"]: ...

# ✅ 无返回值
def reset(self) -> None: ...

# ✅ 生成器 / 可迭代
def iter_lines(path: Path) -> Iterator[str]: ...

# ❌ 反例：缺返回值注解、缺参数注解、裸 dict/list
def parse(data): ...
```

要求：

- 容器写**内置泛型**（`list[str]`、`dict[str, int]`），不要 `List`/`Dict`（Python 3.9+ 风格）。
- 允许多个类型用 `X | None`（3.10+），不要用 `Union`。
- 暂不求解的类型用字符串前向引用（`"User"`）或 `from __future__ import annotations`。
- 类属性也要注解：
  ```python
  class Client:
      timeout: float = 10.0
      session: Session | None = None
  ```
- 公开 API 缺注解 = 代码未完成，不允许提交。

## 5. 文档字符串（Google 风格）

```python
def fetch_page(url: str, *, timeout: float = 10.0, retry: int = 3) -> str:
    """抓取指定 URL 的页面内容。

    超时或 5xx 时会按指数退避重试。

    Args:
        url: 目标地址，需包含 scheme。
        timeout: 单次请求超时秒数。
        retry: 最大重试次数，0 表示不重试。

    Returns:
        页面的文本内容。

    Raises:
        TimeoutError: 重试耗尽后仍然超时。
        ValueError: url 缺少 scheme。
    """
```

要点：

- 第一行是**一句话摘要**，动词开头、省略主语、结尾加句号；后面空一行再展开细节。
- 必写段落（按需）：`Args` / `Returns` / `Yields` / `Raises` / `Attributes` / `Example` / `Note`。
- 每个参数都写，类型信息已由注解表达，docstring 里只解释**语义、单位、边界、默认值含义**。
- 复杂算法 / 非直觉决策要写 `Note:` 说明**为什么这么做**（这类内容同时是 knowledge 的素材）。
- 注释解释 **why**，不解释 **what**；代码自解释的部分不要加注释。

## 6. 命名

| 对象 | 规则 | 例 |
| --- | --- | --- |
| 模块 / 包 | 小写下划线 | `data_loader.py` |
| 类 | 大驼峰 | `DataLoader` |
| 函数 / 变量 | 小写下划线 | `load_page` |
| 常量 | 全大写下划线 | `MAX_RETRY` |
| 私有 | 单下划线前缀 | `_flush` |
| 布尔 | `is_` / `has_` / `should_` 前缀 | `is_ready` |
| 测试 | `test_<行为>_<条件>` | `test_load_missing_key_raises` |

- 不用拼音缩写、不用无意义后缀（`Manager` / `Helper` / `Util` 只在语义确实如此时用）。
- 名称长度与作用域成正比：局部变量可短，跨模块 API 要完整。

## 7. 错误处理与日志

- **只捕获你能处理的异常**；捕获后要么恢复、要么包装成领域异常并附加上下文再抛。
- 禁止 `except: pass` 和 `except Exception: pass`——至少记日志。
- 自定义异常继承合适的内置类型，命名以 `Error` / `Exception` 结尾。
- 用 `logging` 模块，不要 `print` 做诊断输出；库代码不配置 handler，由入口配置。
- 错误信息要能**直接定位问题**：包含关键变量值，避免"出错了"。
- **早失败**：参数校验放在入口，非法状态立刻抛，不要带着脏状态跑下去。

## 8. 惯用法与 Python 3.11 特性

### with 优先

凡是"获取 → 使用 → 释放"模式的资源，**一律优先用 `with`**，不要手写 try/finally：

- 文件、网络连接、数据库会话、锁、临时目录、浏览器页面等，能用 `with` 就 `with`。
- 自带上下文管理器的对象直接用；没有的优先用 `contextlib.contextmanager` 包装，
  或者实现 `__enter__` / `__exit__`（配套的释放逻辑写进类里，不要散落在调用点）。
- 理由：`with` 可读性更好，且异常路径也不会漏释放——多一层缩进换确定性，值得。

### 按项目最低 Python 版本采用兼容特性（见 rules/06）

- **`match` 语句**：对枚举/字面量/数据结构的多分支分发优先 `match`，不写 `if-elif` 长链。
  注意 match 的对象应是"已定义好的类型"（与 §3 静态性一致），不要拿它做运行时动态探测。
- **`ExceptionGroup` + `except*`**：并发/批量任务需要同时上报多个错误时用它，
  不要只抛第一个异常、丢掉其余的。
- **`typing.Self`**：返回自身实例的方法（`return self` 的流式接口、builder、配置器）
  一律注解 `-> Self`，不要写字符串前向引用或手工 TypeVar 模拟。

### 链式调用（流式接口）

- 一个方法需要被**连续反复调用**时（典型：脚本类自动化操作），优先写成链式调用：
  每个操作方法 `return self`，例如 `AutoScript().left_click().right_click().drag_to(x, y)`，
  阅读顺序即执行顺序，非常清晰。
- 链式方法注解用 `typing.Self`；方法用动词命名，每一步不产生隐式的状态跳变。
- 带返回值的查询**不要**混进链里（命令与查询分离），否则链读到一半分不清拿到的是什么。
- 链式接口按对象职责设计，不额外要求模块入口类。

## 9. 代码组织

- 每个模块一个清晰职责，文件超过 ~500 行考虑拆分，**3000 行是硬上限**（见 §2）。
- 拆出的模块按职责暴露函数或类，不强制入口类。
- **包导入**：src/<package>/ 布局从实际包名导入；包内相对导入遵循项目风格。

- import 顺序：标准库 → 第三方 → 本项目，三组之间空一行，**由 `ruff` 的 `I` 规则强制**
  （存量项目遵循已有工具配置，见 `06_python_toolchain.md`）。
- 常量集中在专门模块，不散落各处。
- 不要提交注释掉的大段代码、调试代码、`TODO` 而不说明——要么清理，要么进 todo 文档。

- [ ] 动态能力限定在必要的适配或测试边界，并有验证
- [ ] 变量类型全程一致，所有属性在 `__init__` 或类体中声明并注解
- [ ] import 使用真实包名，包内相对导入符合项目风格

## 11. 说明类文档的更新纪律

- **未得到用户明确要求，不要修改 `README.md` 和其他说明类文档**
  （公开 docs、使用说明、安装指南等）。开发节奏快，功能完成后常会再变，
  每完成一个小功能就回头改文档纯属浪费 token。
  发现"改了 X 文档该跟着改"时：写进交付说明或建一个 todo，**等用户说"更新文档"再动笔**。
- 内部文档（`.agents/docs/**`）不受此限，按 `rules/04` 正常维护。
- **但每个说明类文档必须能判断有效期**：文首标注软件版本号
  （如 `> 适用版本: 1.2.3`）；没有版本号时标注 git 提交哈希
  （如 `> 基线 commit: a1b2c3d`），让用户知道这份文档描述的是哪一版的状态。
