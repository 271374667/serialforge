# 07 · 任务跟踪（todo / checkpoint / explore）

长任务、多功能点开发、大型重构、中断恢复前读本文件。

## 1. 三件套的分工

```
explore/  →  调研结论（这个方案行不行）
   ↓ 我确认可行 → 归档 explore + 建 todo
todo/README.md  →  任务索引与调度表（优先级、顺序、谁在激活）← 唯一调度真源
   ↓ 选中其中一个
todo/NNNN_*.md  →  单个任务的背景与目标
   ↓ 开工
checkpoint/ →  进度快照（做到哪了、下一步是什么、恢复所需上下文）
   ↓ 收尾
归档 todo（移入 _archive/ + 从索引删行）+ 归档 checkpoint
```

索引与任务文档的关系：**索引管"做哪个"，任务文档管"做什么"**，
checkpoint 管"做到哪"。三者不要互相抄内容——重复的内容一定会漂移。

## 2. todo：任务系统（索引 + 单一激活）

### 2.1 三个角色

| 位置 | 作用 | 编号 |
| --- | --- | --- |
| `.agents/docs/todo/README.md` | **任务索引与调度表**——唯一调度真源，一屏看完所有任务的优先级与顺序 | **固定名，不编号，不归档**（与 `ARCHITECTURE.md` 同级的例外，见 `04` §2） |
| `.agents/docs/todo/NNNN_标题.md` | 单个任务正文：背景 / 验收标准 / 阻塞 / 完成记录 | `NNNN_*.md` |
| `.agents/docs/todo/_archive/` | 已完成 / 已废弃任务的历史留存 | `NNNN_*.md` |

**索引是目录，任务文档是正文**：找任务、排优先级、决定下一个做什么 → **只读索引**；
只有被选中的那一个任务才需要读正文。
**禁止**为了"看看有什么任务"去 `ls todo/` 或逐个读任务文档——那正是索引存在的意义（省 token）。

索引长这样（两张表，谁排前面就是下一个做谁）：

```markdown
## 激活中（同时最多一个）

| 编号 | 任务 | 优先级 | 关联 checkpoint |
| --- | --- | --- | --- |
| 0007 | [0007_重构数据层](./0007_重构数据层.md) | 高 | checkpoint/0004_数据层迁移.md |

## 排队中（按 优先级 → 编号 排序）
（同结构，多行）
```

### 2.2 单一激活

- `进行中` 的任务**全项目永远最多一个**，它在索引里占「激活中」表（只有一行）。
- 激活新任务时，旧的自动退回 `排队`（索引里移回「排队中」表）。
- 激活位空出来时（任务完成/废弃）→ 自动激活「排队中」的**队首**（优先级最高、同优先级编号最小）。
- 激活 / 完成 / 改优先级**一律用 `taskmgr.py`**——它同步改「任务文档文首元信息」与「索引」两处。
  **绝不许只改一处**：两边一漂移，索引就不再是真源，§2.6 的"只读索引"前提直接塌掉。

### 2.3 优先级与顺序

优先级 `高 > 中 > 低`（默认 `中`）。排序：**优先级降序 → 编号升序**（先建的先做）。

```bash
python .agents/tools/taskmgr.py priority 0007 高    # 改优先级 + 重排索引
```

**队列腐烂预警（第 34 条）**：排队任务超过 **15 条**时 `check` 会预警——
优先合并同类项、重排优先级，或把远期任务移出 todo/（改放 explore 或直接口头记）。
队列越长越没人看，索引的"下一个做谁"信号就失效了。

### 2.4 什么时候建 todo

| 场景 | 建 todo |
| --- | --- |
| 我提了一个明确的、本次不做的任务 | ✅ |
| 执行中发现了必须做但超出本次范围的问题 | ✅ |
| 我确认可行的调研（explore） | ✅（explore 归档时同步建） |
| 本次会话内就能完成的普通改动 | ❌（直接做） |

**内容要求**：必须写清**任务背景**和**任务目标（可判定的验收标准）**。
已开工的还要在文首 `关联 checkpoint:` 指向对应快照。

```markdown
# 0005_标题
> 状态: 排队  |  创建: 2026-09-01  |  完成: -
> 优先级: 中  |  关联 checkpoint: -

## 背景
## 目标（验收标准）
- [ ] 标准 1
- [ ] 标准 2
## 阻塞 / 依赖
## 完成记录
```

### 2.5 建任务

```bash
python .agents/tools/taskmgr.py add "<任务标题>" --priority 高
```

自动分配编号 → 生成任务文档 → 在索引「排队中」按优先级插入一行。
**建完必须补全「背景」与「目标（验收标准）」**——空壳任务等于没有任务，
下次会话照着索引接手时会一头雾水。

### 2.6 完成任务（三件事，缺一不可）

1. **补全正文**：勾掉验收标准，写「完成记录」（结论 + 关键 commit）。
2. **归档 + 出表**：`taskmgr.py done <编号>` 一条命令做完——
   状态改 `已完成` + 补完成日期 → 移入 `todo/_archive/` → **从 `README.md` 索引删掉该行**。
3. **自动接档**：激活位空了就自动激活队首，并提示下一步读哪个文件。

**归档不出表是违规的**：留在索引里的已完成任务会让"继续任务"流程撞上空文件，
还会被 `check` 报出来。废弃任务同理，用 `taskmgr.py drop <编号>`。

### 2.7 状态流转

```
排队 ──activate──> 进行中（唯一）──done──> 已完成 → _archive/ + 索引删行
  ↑                    │
  └────────────────────┘
                drop → 已废弃 → _archive/ + 索引删行
```

### 2.8 维护命令速查

```bash
python .agents/tools/taskmgr.py list                 # 一屏：激活任务 + 排队清单（"继续任务"先跑这个）
python .agents/tools/taskmgr.py add "<标题>" --priority 高
python .agents/tools/taskmgr.py activate 0007        # 激活（旧的自动退回排队）
python .agents/tools/taskmgr.py priority 0007 高      # 改优先级 + 重排
python .agents/tools/taskmgr.py link 0007 checkpoint/0004_xxx.md
python .agents/tools/taskmgr.py done 0007            # 完成：归档 + 出表 + 激活队首
python .agents/tools/taskmgr.py drop 0009 --reason "方案已废弃"
python .agents/tools/taskmgr.py sync                 # 以任务文档为准重建索引（修漂移 / 迁移存量 TODO）
python .agents/tools/taskmgr.py check                # 校验索引与任务文档一致性
```

`newdoc.py check` 也包含索引校验项（索引缺文件 / 文件没登记 / 激活多个 / 优先级两边不一致）。

## 3. checkpoint：什么时候写

- 长任务**每完成一个功能点**就写/更新一次。
- 也可以在任何"我觉得合适的节点"写：例如跑通了一条链路、做完一批重构、
  或者**即将结束本次会话但任务未完成**（必须写！否则下次无法恢复）。
- 短任务（单文件局部改动）不需要写 checkpoint。

**写入时机优先级**：宁可多写一次，也不要因为没写而丢失上下文。

**长度纪律（第 34 条，check 强制）**：单个 checkpoint 全文 **≤80 行**——
它每次恢复都要**全读**，是成本最高的文档。超过 80 行 `check` 提示精简、
超过 120 行直接报问题。精简方法：命令输出、排查过程、长清单下沉到任务正文或
knowledge，快照里只留「做到哪、下一步、恢复必读的决策」。

```markdown
# 0002_标题
> 任务: todo/0005_xxx.md | 更新: 2026-09-01 | 进度: 3/7
> 最近 commit: a1b2c3d

## 已完成
## 进行中（下一步从这里继续）
## 待办
## 关键决策与上下文（恢复时必读）
## 验证方式（怎么确认这一步是对的）
```

## 4. 恢复中断任务的流程

1. 读 `AGENTS.md`
2. 读**任务索引** `.agents/docs/todo/README.md`（不是逐个读 todo 文档）→
   取「激活中」那一行；它为空就按 §2.2 激活队首
3. 读该任务的 todo 文档 → 取出 `关联 checkpoint:` 指向的文件
4. 读该 checkpoint，从「进行中 / 下一步」继续
5. 核对 checkpoint 里记的最近 commit：`git log --oneline -5`，确认工作区状态与文档一致
   （不一致以**代码现状**为准，并更新 checkpoint）
6. 继续推进 → 更新 checkpoint → 关键节点 commit

**流程图只走索引**：一个文件定位到"当前该做什么"，再最多读两份
（任务正文 + checkpoint）。不要 `ls .agents/docs/todo/` 挨个看，那是索引的活。

## 5. checkpoint 的归档（防上下文污染）

过时的 checkpoint **必须及时归档**——它们描述的进度已经失效，留在 `checkpoint/` 里
会被恢复流程（§4）读到、误导判断，还会白白占用上下文。

**归档时机**（满足任一条即归档）：

- 关联的 todo 已完成（验收标准全部勾掉）→ 对应 checkpoint 一并归档；
- checkpoint 描述的任务已**放弃 / 取消**；
- 快照内容已被**更新的 checkpoint 完全取代**（如任务重启后重建的快照）；
- 任务实际早已收尾，只是收尾时忘了归档。

**动作**：

1. 优先用脚本：`python .agents/tools/newdoc.py archive <文件路径>`——
   自动移入同分类 `_archive/` 并在文首补归档时间与原因；
2. 没有脚本环境就手动移入 `checkpoint/_archive/`，文首补一行：
   `> 归档时间: YYYY-MM-DD  |  归档原因: 任务已完成`（原因照实写：完成 / 取消 / 被取代）。
3. **同步清理引用**：归档前检查是否有 todo、其他 checkpoint、AGENTS.md 或交接页引用它，
   引用一并修正或删除，避免制造断链。
4. 归档 ≠ 删除：历史价值保留在 `_archive/`，需要时还能翻出来复盘。

**例外——动态交接页不归档**：若项目有一个唯一动态状态源
（如 `checkpoint/0001_当前进度与接手指南.md`），它**只更新内容、不归档**，
除非整个项目阶段翻篇。

**两个检查节点（在这两个时点必须扫一遍 `checkpoint/`）**：

| 节点 | 触发时机 | 要做什么 |
| --- | --- | --- |
| **① 交接任务时** | 写交接 checkpoint、准备开新会话（见 `rules/01` §7） | 归档所有已过时快照，确保新会话读到的 `checkpoint/` 里**只剩有效内容**；归档完再输出启动提示词 |
| **② 任务完成时** | **阶段性任务完成**（一个功能点/一个里程碑收尾）或**全部任务完成** | 完成的快照连同对应 todo 一起归档；任务还有后续阶段时，只归档本阶段快照、保留/新建下一阶段的 |

两个节点共用的检查步骤：

1. 列出 `.agents/docs/checkpoint/*.md`（不含 `_archive/`）；
2. 逐个判断是否仍有效：任务还在进行？还是已完成 / 已取消 / 已被更新的快照取代？
3. 无效的 → `newdoc.py archive` 归档 + 清理引用；**有效的一律保留，不要误归档**；
4. 归档后重新确认：`checkpoint/` 里剩下的都是"还需要继续照着做"的快照。

**目的**：过时的 checkpoint 会被恢复流程（§4）和交接提示词读到，误导判断、污染上下文——
宁可多归档，也不要让新会话在一堆失效快照里猜哪个才是当前进度。

## 6. 长任务的提交节奏

配合 `05_git_and_commits.md`：

- 每完成一个**可验证**的功能点 → `git commit`
- 每完成一次**行为不变**的重构 → 单独 commit
- 准备做大范围改动前 → 先 commit 一个干净点作为回退锚点
- 会话结束前 → 即使任务没完成也要 commit（WIP 也要留），并写/更新 checkpoint

## 7. explore：调研任务

我让你"调研一下 / 查一下 / 这个方案可行吗"时：

1. 写 `.agents/docs/explore/NNNN_*.md`：问题、方法与范围、候选方案对比、结论与建议、风险
2. 在回复里给出摘要和我的决策点
3. **我确认可行** → 归档该 explore（注明归档原因与去向）+ 创建对应 todo
4. **我否决** → 归档并注明否决原因（避免以后重复调研）

## 8. 与 knowledge / questions 的边界

- 任务过程中**学到的可复用知识**（为什么这样设计、这个参数怎么调）→ knowledge
- 任务过程中**踩到并修好的坑** → questions
- 任务**本身的进度状态** → checkpoint / todo

三者不要混写：checkpoint 里不要长篇科普，knowledge 里不要写"今天做到了第 3 步"。
