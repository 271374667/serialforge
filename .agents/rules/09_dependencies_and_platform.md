# 09 · 依赖引入与平台约束

考虑引入第三方库、或判断某方案在本机能否跑时读本文件。

## 1. 依赖决策权归我（硬约束）

> **在需求评估阶段，如果发现引入第三方库可以大幅加快进度 —— 告诉我，由我权衡。**
> 不要默认自己造轮子，也不要默认装库。

**报告格式**（一句话 + 一小表即可）：

```
建议引入：<库名> <版本>
用途：<解决什么问题>
收益：省掉约 xxx 行自研代码 / 直接获得 xxx 能力
代价：新增 N 个传递依赖、许可证 <MIT/Apache-2.0/...>、体积 x MB、维护活跃度 <最近发版时间>
自研替代方案：约需 xxx 行，风险是 xxx
```

**关键判断维度**：许可证是否商用友好、是否还在维护、是否有 Windows 轮子、
传递依赖是否过重、是否引入与现有依赖的版本冲突。

得到明确答复前：不要安装、不要写依赖它的代码。可以先把设计写成 explore 报告。

## 2. 倾向自研的情况

- 核心业务逻辑 / 差异化竞争力（不该外包给库）
- 只需其中 5% 功能却要背上整个重型依赖
- 许可证不允许、或已停止维护
- 传递依赖会污染环境（尤其是带 C 扩展的重型库）

## 3. 目标平台（固定）

- **开发平台：Windows 10 64bit / Windows 11 64bit**
- **发布平台：按项目实际声明，不能仅从开发平台推断**
- **不考虑 Linux 打包与分发**（可为未来留口子，但不要为它增加复杂度）

因此：

- 选库时确认提供兼容的纯 Python wheel（如 py3-none-any）或匹配 ABI 的 win_amd64 wheel；只有 sdist（需要本地编译）的依赖要提前预警
  （Windows 上常常缺编译器，代价很高）。
- 不写 Linux-only 的路径、信号、进程模型假设。
- 环境标记只写 `sys_platform == 'win32'`，不要维护 Linux 分支。
- 需要外部命令行工具时，确认它有 Windows 版本，并把路径解析做成可配置。

## 4. Windows 常见坑（写进 knowledge 的候选）

- 默认编码非 UTF-8 → 文件读写一律显式 `encoding="utf-8"`；必要时
  `sys.stdout.reconfigure(encoding="utf-8")`。
- 路径长度 260 限制 → 用 `pathlib` + 必要时长路径前缀。
- 换行符 CRLF → 文本比较前先 normalize；git 建议 `core.autocrlf=input`。
- 文件占用导致无法删除/覆盖（尤其 Windows 上打开的文件）→ 确保上下文管理器释放句柄。
- 大小写不敏感的文件系统 → 不要只靠大小写区分两个模块名。
- 多进程需用 `if __name__ == "__main__":` 保护。

## 5. 依赖变更流程

1. 说明并获我同意
2. `uv add <pkg>`（开发依赖加 `--dev`）
3. 确认 `pyproject.toml` 与 `uv.lock` 都更新并提交
4. 跑受影响的测试；依赖变更影响全局时跑全量
5. 若引入了非直觉的取舍 → 写一条 `knowledge/software/` 记录（含选择理由）
