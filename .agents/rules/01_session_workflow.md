# 01 · 会话工作流（每次会话必读）

本规则定义 AI 在本项目中的**标准动作序列**。它是唯一无条件必读的规则文件。

## 1. 会话启动（四件事，缺一不可）

```
1) 读项目根目录的 AGENTS.md
2) 读 .agents/ARCHITECTURE.md 的必读区——第 1、2、3、6 节（无条件必读，≤150 行）
3) 按 AGENTS.md 第 2 节「规则索引」只读本次任务需要的规则文件（通常 1–3 份）
4) 读任务索引 .agents/docs/todo/README.md（一屏），确认激活任务与队列
   —— 只要本次会话没有明确的既定目标，就走 §4「继续任务」流程
```

**禁止**跳过任何一步直接写代码。用户的需求描述再详细，也不能替代读 AGENTS.md——
因为硬约束（分支、禁推、根目录纪律）只在那里定义。

**第 2 步只读必读区**：`ARCHITECTURE.md` 是架构的唯一真源（活文档，不编号不归档，
见 `15_architecture_doc.md`）。读它取代的是"翻目录树 + 读若干源文件猜职责"的探索成本，
省 token 的关键在于**不猜错**。

- **必读区（第 1、2、3、6 节）**：项目是干什么的、外部形态、模块地图、关键不变量——
  回答"去哪改、不能碰什么"，**每次会话都读**，合计不超过 150 行。
- **按需区（第 4、5、7、8 节）**：交互关系、状态与外部边界、深潜入口、变更日志——
  只在**要动结构 / 要交接 / 要深入某模块 / 要查变更史**时读，长度不限。

整份读完对小任务是浪费；分区读是把固定成本钉死，同时不限制该写多少。

**关于 14 号规则的一次性纪律**：`14_new_project_stack.md`（新项目选型推荐）**只在
新建项目、正在做依赖与技术栈分析时读一次**。项目依赖已确定、或这是存量项目 →
**禁止再读它**（省 token），依赖问题一律走 `09_dependencies_and_platform.md`。
若它已在 `.agents/rules/_archive/` 下，说明选型早已完成，同样不要读。

## 2. 动代码之前的检查清单

- [ ] `git branch --show-current` → 快速迭代阶段应直接在 `dev` 上工作；稳定阶段才从 `dev` 拉自己的
      `feat/<name>` / `fix/<name>` 分支（见 `05_git_and_commits.md` §1）。
      **绝不在 `master` / `main` 上直接动手**，不自动切主干、不自动 stash
- [ ] `git status` → 工作区是否干净，是否有别人（别的会话）在途的改动；
      要同时跑多个会话就用 `git worktree` 做物理隔离（见 `05` §9）
- [ ] 判断任务规模 → 决定是否需要 checkpoint / todo（见下）
- [ ] 是否涉及第三方库 → 是则**先报告，等确认**（见 `09_dependencies_and_platform.md`）
- [ ] 是否涉及新目录 / 临时文件 → 见 `08_layout_and_temp.md`

## 3. 任务规模判定

| 规模 | 判据 | 动作 |
| --- | --- | --- |
| 小 | 单文件、局部改动、不涉及架构 | 直接做，做完更新文档（如有） |
| 中 | 跨 2–5 个文件，或 1 个完整功能点 | 建 checkpoint，功能点完成后 commit |
| 大 | 多个功能点 / 大型重构 / 预计跨多次会话 | 建 todo（登记背景目标）→ 建 checkpoint → **每个关键节点 commit** |

## 3.5 「继续任务 / 接着做」的专用流程（第 33 条）

**触发**：用户说「继续 / 接着做 / 继续之前的任务 / 上次那个做完没 / 接下来做什么」
或类似意思，且**当前上下文没有在途任务**（新会话、或本次会话还没接过任何具体任务）。
不要逐字匹配，识别意图即可。

**四步**：

1. **只读索引**：`.agents/docs/todo/README.md`（必要时 `taskmgr.py list`）。
   **禁止**为找任务去 `ls todo/` 或逐个读任务文档——索引一屏就够，那是它存在的全部意义。
2. **有激活任务** → 它就是当前任务：读它的任务文档 → 读它 `关联 checkpoint`
   → 从 checkpoint 的「进行中 / 下一步」继续；没有 checkpoint 就按任务文档里的验收标准推进
   （中/大任务记得先 `newdoc.py new checkpoint` 建一个并 `taskmgr.py link` 过来）。
3. **激活位为空** → 取「排队中」队首（优先级最高、同优先级编号最小）→
   `taskmgr.py activate <编号>` → 回到第 2 步。
4. **两张表都空** → 明确告诉用户「任务队列是空的」，问要做什么。
   **不要自己从 README / 代码 / git log 里脑补一个任务出来**——猜出来的任务只会浪费一轮上下文。

**接手后要向用户回一句话**：当前接的是哪个任务（编号 + 标题）、从哪一步继续。
让用户有机会在第一时间纠正"接错了"。

## 4. 执行中的行为准则

- **小步推进**：完成一个可验证的子目标就停下来验证（跑测试 / 跑命令），不要攒一大坨再验。
  但验证走**分层测试策略**（见 `06_python_toolchain.md` §4）：小改动只跑相关测试，
  全量测试留到大阶段完成时，不要每次都全量跑浪费时间。
- **不要假装完成**：跑不通就如实说跑不通，并给出错误信息与已尝试的方案。
- **不要扩大范围**：不要顺手重构无关代码、不要"优化"没被要求动的地方。
  确有发现 → 记入 todo 或口头提出，由我决定。
- **遇到歧义**：优先按规则兜底执行，并在回复中说明你的判定依据，方便我纠正；
  只有涉及**不可逆操作**（删除、推送、大范围重构、引入依赖）时才必须停下询问。

## 5. 收尾（同样重要）

- [ ] 跑相关测试 / 验证命令，确认没破坏既有行为（分层策略：小改动只跑定向测试；
      全量测试只在**大阶段完成**的收尾节点跑，见 `06_python_toolchain.md` §4）
- [ ] （Python 项目）按项目工具检查本次修改文件，审阅自动修复 diff，保护用户已有改动
- [ ] （Python 项目）使用已选类型检查器，记录基线与本次结果；迁移工具链单独评估（见 `06`）
- [ ] 按**可回退单元**提交：`git add <明确路径>` → `git commit`，提交信息由**我自己撰写**
      （中文 Conventional Commits + `AI-Used-For` / `AI-Prompt` trailer，**禁止 AI 签名**）；
      `oco` / opencommit 已弃用。探路阶段的 `wip` 提交收尾前用 `git rebase -i` 压成原子提交——
      **跑 `rebase` 前先做一份含 `.git/` 的整仓快照**，中断后先体检再动手（见 `05` §4、§5、§6、§10）
- [ ] 更新当前任务的 checkpoint：`已完成 / 进行中 / 下一步`
- [ ] todo 状态流转：`排队 → 进行中 → 已完成(归档)`——**一律走
      `taskmgr.py`（activate / done / drop）**，它会同步更新任务文档文首元信息与
      `todo/README.md` 索引（归档即出表）；**禁止**只用 `newdoc.py archive` 归档 todo
      （那样索引会残留已完成任务，见 `07` §2.6）
- [ ] **任务完成时（阶段性或全部完成）**：检查 `.agents/docs/checkpoint/`，
      把已完成 / 已取消 / 已被取代的快照归档到 `checkpoint/_archive/`（见 `07_task_tracking.md` §5 检查节点②）
- [ ] 本次**引入了新的概念/设计决策** → 写 knowledge；**修掉了一个坑** → 写 questions
      （判定标准见 `04_docs_system.md`，常规改动两者都不写）
- [ ] 临时产物清理或归入 `temp/NNNN_xxx/`
- [ ] **架构总览是否要更新**：本次改动是否动了模块职责 / 依赖方向 / 对外接口 / 运行与交付方式？
      是 → 更新 `.agents/ARCHITECTURE.md`（正文 + 文首基线 commit + 变更日志顶部加一行，见 `15` §6）；
      否（bug 修复、小迭代、不改职责的重构）→ 不改，但这一眼必须过
- [ ] **发现文档与代码不符 → 当场改**（`15` §6 节点⑤）：干活过程中若发现
      `ARCHITECTURE.md` 描述与实际代码对不上（职责、依赖、不变量过时了），
      **当场修正并在变更日志加一行**，不必等四个计划节点——过时的地图比没有地图更危险

## 6. 多工具兼容约定

AI 工具可能是 Codex、Claude Code、WorkBuddy 或 Cursor。为了保证行为一致：

- 所有约定**只在 `AGENTS.md` 与 `.agents/rules/` 中定义一次**，其他工具的配置
  （`CLAUDE.md`、`.cursorrules` 等）只做一行转发，不复制内容，避免两份规范漂移。
- 路径一律使用**相对项目根**的 POSIX 风格路径（`.agents/rules/02_code_style.md`）。
- 不使用任何单一厂商专有的语法或 frontmatter 作为规范载体。

## 7. 会话交接（上下文将尽时立即执行）

当用户表达「上下文过长 / 快满了 / 要开始新的对话 / 开新会话 / 保存进度准备重开」
或类似意思时，**立刻停下手上的任务**——不要把手头的修改做完再交接，
除非用户当场明确说"做完这个再停"。然后按顺序执行：

1. **冻结工作**：停止写代码；未完成的修改留在工作树，不做半途提交、不回滚。
2. **更新架构总览**：本次是否动了模块职责 / 依赖方向 / 对外接口 / 运行与交付方式？
   是 → 先改 `.agents/ARCHITECTURE.md`（含文首基线 commit 与变更日志一行），**再写交接快照**
   ——新会话第一个读的就是它的必读区，写完再冻结进度（见 `15_architecture_doc.md` §6 节点①）。
3. **清理过时 checkpoint**（`rules/07` §5 检查节点①）：扫一遍 `.agents/docs/checkpoint/`，
   把已完成 / 已取消 / 已被取代的快照归档到 `checkpoint/_archive/` 并清理引用——
   **先归档、再写新的交接快照**，保证新会话读到的目录里只剩有效进度。
4. **写交接 checkpoint** 到 `.agents/docs/checkpoint/`（优先
   `python .agents/tools/newdoc.py new checkpoint "<任务名>-handoff"` 自动编号），
   按 `07_task_tracking.md` 模板填全：
   任务背景与目标（关联 todo） / 已完成（**含最近 commit 哈希**） /
   进行中与下一步（**精确到文件路径和具体操作**） / 关键决策与上下文 / 未验证事项与风险。
   **顺手确认任务索引**：该任务在 `todo/README.md` 里处于「激活中」且 `关联 checkpoint`
   指向刚写的这份快照——没有就 `taskmgr.py link <编号> checkpoint/000X_xxx.md` 补上，
   否则新会话按 §3.5 接手时会找不到断点。
5. **更新动态交接页**（若存在 `checkpoint/0001_*` 之类的唯一状态源，同步"当前阶段 / 当前任务"）。
6. **输出新对话启动提示词**（代码块包裹，让用户一键复制）：

```text
请接手 <项目名> 的一个进行中任务，上下文交接如下：

- 项目根目录：<绝对路径>
- 启动步骤：先读 AGENTS.md → 读 .agents/ARCHITECTURE.md 的必读区（第 1、2、3、6 节）
  → 按其索引读 .agents/rules/01_session_workflow.md
  → 读任务索引 .agents/docs/todo/README.md（激活任务：000Y_<名称>）
  → 读交接 checkpoint：.agents/docs/checkpoint/000X_<名称>.md
- 任务一句话：<当前任务是什么、为什么做>
- 下一步：从 checkpoint 的「进行中 / 下一步」继续，不要重做已完成的部分
- 注意：遵守 AGENTS.md 的全部硬约束；有疑问先问我，不要凭猜测改代码
```

**要点**：提示词里引用的文件必须真实存在（输出前确认）；checkpoint 写完才算交接完成。
