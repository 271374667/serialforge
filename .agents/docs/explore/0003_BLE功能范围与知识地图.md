## 1. 先看结论

serialforge 可以规划为“串口 + BLE 通讯库”。BLE 应拥有独立的扫描、客户端、服务端及 GATT 数据模型；仅把串口后端换成蓝牙后端，不能完整支持读写、订阅和开服务。

本次整理 **10 类、100 个候选功能项**：**49 项常用基线、26 项工程建议、19 项按需可选、6 项建议留在库外**。这是为本项目划分的产品清单，不是 BLE 标准规定的功能总数，也不表示所有项目都需要 100 项。常用程度按 Windows GATT API、Bleak 等主流接口覆盖及设备通讯场景定性判断，不代表市场占比统计。

你的明确目标已覆盖：本机开启 GATT 服务、客户端、服务端、读、写、订阅。其余条目均供取舍；“常用”表示建议放入第一版产品范围，不代表已经获得实现授权。

关键选型结论：**Windows 上不能仅依靠 Qt Bluetooth 满足这组需求**。其官方支持表没有 Windows BLE Peripheral；当前更合适的候选是 Windows 原生 WinRT GATT API + PyWinRT + QtCore 线程桥接，细节及限制见配套计划。[Qt 官方支持表](https://doc.qt.io/qt-6/qtbluetooth-index.html)、[Windows GATT 命名空间](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile)

## 2. “开启服务”和“同时支持”的含义

| 表述 | 本报告采用的含义 | 需要明确的边界 |
| --- | --- | --- |
| 开启 BLE 服务 | 在 PC 上建立本地 GATT 服务树，发布服务，并广播可连接入口 | 不是 TCP 监听端口，也不是注册 Windows Service |
| 客户端 | 发现远端服务/特征，主动读写，订阅通知或指示 | 不是只能接收数据；客户端可以向服务端写数据 |
| 服务端 | 提供本地特征，处理远端读写，向订阅者推送 | 不是只能发送数据；服务端也会收到客户端写入 |
| 库同时支持两种角色 | 同一个发行包提供客户端和服务端能力 | 这是基础目标 |
| 同一进程同时运行两种角色 | PC 既连接设备 A，又让手机 B 连接本机 | 建议支持，见 B07；同适配器并行需单独实测 |
| 同时连接多个 BLE 设备 | 多个独立客户端会话互不串数据 | 建议支持，见 B06；不保证固定最大数量 |
| 串口和 BLE 同时运行 | 串口会话及 BLE 会话在同一 Qt 应用内共存 | 建议作为基础验收，见 B05 |
| PC 连接自己的本地 BLE 服务 | 使用同一适配器进行无线回环 | 不作为支持前提；用手机、开发板或第二台 PC 验证 |
| 后台长期运行 | 进程持续运行期间提供服务 | 系统服务、登录前运行、休眠中持续广播另行评估 |

GAP 的 Central/Peripheral 是连接建立角色，GATT 的 Client/Server 是数据访问角色，二者不能严格画等号。常见产品把 Central 与 Client、Peripheral 与 Server 配对，但协议允许更复杂组合；第一版建议先覆盖这些常见组合。[Microsoft BLE 角色说明](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/bluetooth-low-energy-overview)

## 4. BLE 知识地图

下面是使用方和实现方必须先对齐的概念；它们不重复计入 100 项功能。

| 概念 | 是什么 | 对这个库的直接影响 |
| --- | --- | --- |
| BLE 与经典蓝牙 | BLE 使用 LE 协议体系；经典蓝牙 SPP/RFCOMM 是另一条路线 | BLE 通常不会自动生成 COM 口，不能靠 pyserial 直接通信 |
| GAP | 负责发现、广播和连接等访问行为 | 扫描、广播和 GATT 操作分别建模 |
| Central / Peripheral | 常见的主动建立连接方 / 接受连接方 | 角色支持及同机并行需要探测 |
| Observer / Broadcaster | 扫描广播 / 发送无需连接的广播 | Beacon 不一定有 GATT 服务 |
| GATT | 对属性的发现、读写和推送模型 | 原生 BLE 层暴露端点，不暴露波特率和 DTR/RTS |
| ATT | 承载属性访问、响应、错误及推送的协议 | ATT 完成和业务命令完成必须分层 |
| Service | 将相关特征组织在一起 | 服务 UUID 不是连接端口 |
| Characteristic | 有属性、权限和值的通信端点 | 相同特征可以同时可读、可写和可通知 |
| Descriptor | 特征附属元数据及配置 | 通用读写可用，但系统生成项不可重复管理 |
| UUID | 属性类型的标识；标准短 UUID 映射到 Bluetooth Base UUID | 自定义业务使用 128-bit UUID；UUID 不是某次连接的对象身份 |
| Handle / 实例 | 一次服务数据库中的具体属性位置 | 重复 UUID 需要消歧，重连/固件变化后旧句柄可能失效 |
| Characteristic Properties | 声明这个端点支持哪些操作 | 支持 Write 不代表无需认证即可写 |
| Permissions / Protection | 谁在什么安全条件下可以访问 | 客户端错误和服务端保护级别需明确 |
| Advertisement / Scan Response | 无连接广播及主动扫描补充信息 | 广播可能只有部分字段，不能假定第一包就是完整设备资料 |
| RSSI / Tx Power | 接收信号强度 / 发射功率信息 | 可做粗略接近判断，不能承诺精确距离 |
| Public / Random / Private Address | 公共地址及不同随机/隐私地址方式 | 地址可能改变；业务稳定身份需设备协议或系统绑定支持 |
| Pairing | 协商安全关系的过程 | 有些公开端点无需配对；连接成功不表示已配对 |
| Bonding | 保存配对产生的密钥等长期关系 | 由 OS 管理；库不落盘复制链路密钥 |
| Encryption / Authentication | 链路加密与对端认证等安全条件 | 配对方式、设备能力和保护级别共同决定安全性 |
| Notification | 服务端推送，不要求 ATT 层逐条确认 | 无业务送达保证；链路层可靠机制不能当应用层确认 |
| Indication | 服务端推送，要求 ATT 层确认 | 确认通常由协议栈完成，不等于 UI/业务已处理 |
| CCCD，0x2902 | 客户端对某特征通知/指示的配置 | 订阅是状态；恢复订阅不能只重连事件回调 |
| ATT MTU | 一次 ATT 协议数据单元大小 | 常见默认 MTU 23 时，普通通知/写命令载荷最多 20 字节；不是 BLE 固定只能发 20 字节 |
| Long Read / Long Write | 标准定义的跨多次 ATT 访问长属性过程 | 与自定义 UART 分包、可靠事务分别处理 |
| Connection Parameters / PHY / DLE | 连接时序、物理层及链路数据长度能力 | 影响吞吐/延迟/功耗，往往不是桌面库可自由控制的开关 |
| Service Changed / GATT Cache | 远端数据库改变及系统缓存 | 升级后重新发现和失效处理必须可用 |
| Profile / DFU | 特定功能的使用约定 / 固件升级流程 | 基础库只给通用机制，具体设备协议外置 |

知识依据：[Bluetooth SIG LE Primer](https://www.bluetooth.com/wp-content/uploads/2022/05/Bluetooth_LE_Primer_Paper.pdf)、[GATT 协议规范](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-62/out/en/host/generic-attribute-profile--gatt-.html)、[GATT 特征与描述符补充规范](https://www.bluetooth.com/specifications/gss/)。表中“对库的影响”是本项目的设计推导。

### 4.1 读、写、订阅、推送的方向

| 操作 | 谁发起 | 数据主要方向 | 对端是否必须订阅 |
| --- | --- | --- | --- |
| Read | 客户端 | 服务端值返回客户端 | 否 |
| Write With Response | 客户端 | 客户端写值到服务端，再收到 ATT 结果 | 否 |
| Write Without Response | 客户端 | 客户端写值到服务端 | 否 |
| Subscribe | 客户端 | 配置服务端的 CCCD，并准备本地接收 | 是建立订阅本身 |
| Notify / Indicate | 服务端 | 服务端值推送到客户端 | 是 |
| 更新本地特征值 | 服务端应用 | 更新本地状态，供后续读取 | 不自动意味着推送 |

客户端“发送数据”往往是 Write；服务端“发送数据”往往是 Notify/Indicate。接口应反映实际操作，而不是统一叫 send 后隐藏可靠性区别。

### 4.2 容易混淆的六件事

1. **写成功不等于命令执行成功**：ATT 写响应只证明这一步访问被接受。电机启动、存储完成等需要设备自己的业务响应。
2. **20 字节不是固定上限**：普通单包有效载荷常为 MTU 减去协议开销；Windows 管理 MTU，应用不能要求任意数值。通知还要按订阅客户端的实际上限检查。[Windows MaxPduSize](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattsession.maxpdusize)、[MaxPduSizeChanged](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattsession.maxpdusizechanged)
3. **不能任意拆写**：连续写两次特征，设备可能执行两次命令，而不是拼接为一条。UART 分包必须由双方约定。
4. **BLE 空值不能当作串口空读取**：一次 GATT 读取或通知可以携带零长度值；既有 received 非空规则不能直接套用。
5. **广播空间不是服务树大小**：传统广播数据有 31 字节预算，AD 类型和长度也占空间；扩展广播另算。多个服务可以存在于数据库中，却未全部出现在广播里。[Bluetooth LE Primer](https://www.bluetooth.com/wp-content/uploads/2022/05/Bluetooth_LE_Primer_Paper.pdf)
6. **广播字段并非全部可配置**：Windows 独立 AdvertisementPublisher 限制本地名、Flags、服务 UUID 等字段；应使用 GATT ServiceProvider 发布可连接服务，不能混淆两种入口。[AdvertisementPublisher 限制](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.advertisement.bluetoothleadvertisementpublisher)
