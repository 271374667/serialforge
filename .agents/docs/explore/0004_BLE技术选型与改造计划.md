## 1. 建议结论与证据等级

建议在现有串口能力旁增加独立 `serialforge.ble`，提供 BLE Scanner、GATT Client、GATT Server 三种职责，再增加可选 UART 通道以接入现有 Spec。底层优先验证 **PyWinRT 调用 Windows 原生 BLE API，IO 在专用工作线程执行，结果经 QtCore 排队投递主线程**。

这条路线能保留“仅 QtCore、不使用 asyncio、不使用多进程”的既有约束。它不是直接采用一套现成完整 BLE 库：OS 负责协议栈，PyWinRT 负责 API 投影，本库仍需实现生命周期、队列、错误映射和 Qt 交付契约。

| 证据等级 | 本次已做到 | 不能据此声称什么 |
| --- | --- | --- |
| 文档证据 | 查阅 Qt、Microsoft、Bluetooth SIG、Bleak、PyWinRT 和 Bless 的一手资料 | 不等于本机硬件支持 |
| 元数据证据 | 读取 PyPI JSON，核对版本、Python 范围、Windows wheel、依赖约束及许可证 | 不等于已经解析安装或成功导入 |

## 2. 已核实的平台事实

### 2.1 Windows 能做 GATT Server，Qt Windows 后端不能完整覆盖

Windows 有 GATT 客户端和服务端原生 API，相关服务端入口自 Windows 10 1703 起提供；这只是 API 引入版本，不是本库应承诺的最低系统版本。Qt Bluetooth 官方支持表至本次查询仍未列出 Windows BLE Peripheral，QLowEnergyController 也明确说明此限制。[Windows BLE 角色](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/bluetooth-low-energy-overview)、[GattServiceProvider 版本要求](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattserviceprovider)、[Qt QLowEnergyController](https://doc.qt.io/qt-6/qlowenergycontroller.html)

必须在运行时检查适配器的 Central/Peripheral 能力；操作系统版本和适配器宣传的蓝牙版本都不足以保证可开服务。[IsPeripheralRoleSupported](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothadapter.isperipheralrolesupported)、[IsCentralRoleSupported](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothadapter.iscentralrolesupported)

### 2.2 不使用 asyncio 仍有可验证的 WinRT 路线

PyWinRT 当前文档明确给出三种使用异步操作的方式：同步 `get()/wait()`、Python await、`completed` 完成回调。`get()/wait()` 自 3.2 提供，不能在 STA 线程调用；完成回调适用于不使用 asyncio 的 GUI 应用。[PyWinRT 类型与异步操作](https://pywinrt.readthedocs.io/en/stable/types.html)

因此优先使用完成回调驱动工作线程状态机；只在必要且有期限控制的 MTA 工作线程使用同步等待。禁止在主线程阻塞等结果，也不能让一个无限等待阻止整个 BLE 后端处理停止请求。这是根据 API 推导的设计，仍需验证 Qt 绑定、COM apartment、GIL 和回调生命周期的组合。

### 2.3 桌面部署与权限不能按 UWP 示例直接下结论

Microsoft GATT 教程使用声明 bluetooth capability 的应用包示例；原生命名空间同时说明桌面应用可以使用。PyWinRT 也提醒部分 WinRT API 需要 package identity。因此不能直接断言“普通 Python 必须打 MSIX”，也不能承诺所有 API 在未打包宿主下都可用。[GATT 命名空间](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile)、[PyWinRT API 适用性提醒](https://pywinrt.readthedocs.io/en/stable/api/index.html)

首个验证门槛必须包含：普通 `uv` 启动的 Python/QtCore 程序，无 package identity 时完成服务创建、广播、手机读写及订阅；再验证实际下游使用的打包 EXE。需要打包或额外权限的能力单独报告，不把部署责任隐藏在库里。

### 2.4 数据长度、广播和停止行为由平台限制

Windows 管理 MTU，应用可观察 `MaxPduSize` 和变化事件，不能任意设置。[MaxPduSize](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattsession.maxpdusize)、[MaxPduSizeChanged](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattsession.maxpdusizechanged)

独立 AdvertisementPublisher 有系统保留字段和共享广播资源限制；可连接 GATT 服务使用 ServiceProvider 发布，二者不能互相冒充。[AdvertisementPublisher](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.advertisement.bluetoothleadvertisementpublisher)、[GATT 广播参数](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattserviceprovideradvertisingparameters)

停止广播、关闭本库对象、远端实际断链是不同动作。其他进程也可能持有同一设备连接；服务停止后是否仍能发现旧服务、是否还会到达旧请求，需要写入真实验收。不能承诺全局强制断开所有对端。

## 3. 后端候选比较

| 路线 | Windows 客户端 | Windows 服务端 | QtCore / 无 asyncio | 主要代价 | 建议 |
| --- | --- | --- | --- | --- | --- |
| Qt Bluetooth | 支持常见 GATT 客户端 | 官方不支持 Peripheral | 不需要 asyncio，但新增 QtBluetooth，违反当前仅 QtCore 边界 | 三绑定差异、额外 Qt 模块、双角色目标无法满足 | 不作为完整方案 |
| Bleak 3.0.2 | 成熟，发现/读写/订阅覆盖好 | 本身是 GATT Client 库 | 正常接口依赖持续运行的 asyncio loop | 需修改项目禁止 asyncio 的契约；服务端另找方案 | 只有你接受改变约束后才重评 |
| Bleak + Bless 0.3.0 | 客户端由 Bleak 提供 | Bless 提供服务器封装 | 示例/接口采用 asyncio | 当前发行版依赖存在冲突，线程及安全能力也需评估 | 不推荐直接组合 |
| PyWinRT 3.2.1 + 原生 BLE | 原生 API 支持 | 原生 GATT Server 支持，依硬件 | 可采用 completed 回调和 QtCore 桥接 | 本库需要建设 Windows 后端；可用性必须实测 | 首选验证候选 |
| 自建 C++/WinRT 扩展 | 可以封装 | 可以封装 | 可通过回调接入 QtCore | 维护 C++、Windows ABI、编译与 wheel，多版本成本高 | PyWinRT 无法覆盖关键能力时的后备 |
| 外接 BLE 模块，经串口控制 | 取决于固件 | 取决于固件 | 易接当前串口层 | 依特定硬件及 AT/二进制命令，不是系统蓝牙通用实现 | 独立硬件插件场景 |

Bleak 的定位和循环要求见[官方功能说明](https://bleak.readthedocs.io/en/stable/)与[运行循环要求](https://bleak.readthedocs.io/en/stable/troubleshooting.html)；Bless 的服务器能力和 asyncio 用法见[官方仓库](https://github.com/kevincar/bless)与[服务器示例](https://github.com/kevincar/bless/blob/master/examples/server.py)。Qt 方案即使加入模块，也不能因此获得 Windows Peripheral。

### 3.1 当前 Bleak / Bless 组合的具体版本问题

2026-10-14 直接查询 PyPI 元数据得到：

| 分发包 | 当前返回版本 | 关键约束 |
| --- | --- | --- |
| bleak | 3.0.2 | Windows 下需要多项 `winrt-* >=3.1` |
| bless | 0.3.0 | 依赖 `bleak>=1.1.1`；Python >=3.12 时固定多项 `winrt-* ==2.0.0b1` |
| winrt-runtime 及本次候选 WinRT 命名空间包 | 3.2.1 | Python >=3.9，包含 CPython 3.11–3.14 的 win_amd64 wheel |

所以 **Bleak 3.0.2 与 Bless 0.3.0 在 Windows + Python >=3.12 上不能同时满足这些 WinRT 约束**。这里是元数据层面的版本冲突，不是已经运行 uv 的安装实验，也不意味着历史版本、源码主分支或维护修订永远不可用。降级、打补丁或维护 fork 都会新增成本，且仍不能解决本项目禁止 asyncio 的基本约束。

可复核原始来源：[Bleak JSON](https://pypi.org/pypi/bleak/json)、[Bless JSON](https://pypi.org/pypi/bless/json)、[WinRT GATT JSON](https://pypi.org/pypi/winrt-Windows.Devices.Bluetooth.GenericAttributeProfile/json)。版本是查询快照，实施前应重新核查。

## 4. 现有架构为什么不能直接加一个 BLE Transport

以下是本次实际阅读源码得到的耦合点；尚未修改这些文件。

| 现有位置 | 当前行为 | BLE 引入后的必要变化 |
| --- | --- | --- |
| `src/serialforge/protocols.py:TransportProtocol` | 阻塞 read/write、清输入缓存、DTR/RTS、串口缓冲大小 | 原生 GATT 需要端点、操作类型、订阅及服务端请求；不能用空实现假装符合串口协议 |
| `src/serialforge/transport/serial_transport.py:SerialTransport` | pyserial 端口枚举、端口打开、字节流 IO | 保持串口职责；新增 WinRT BLE 后端，避免混入无线角色分支 |
| `src/serialforge/discovery/` | COM、VID/PID、波特率探测、请求探测、缓存 | BLE 以广播、服务 UUID、系统标识发现；独立扫描模型，不复用串口探测算法 |
| `src/serialforge/models.py:DeviceInfo` | 串口设备信息 | 增加 BLE 设备模型；不把 MAC 塞入 port、把 UUID 塞入 VID/PID |
| `src/serialforge/connection/serial_forge.py:scan/connect` | 每次操作先断开本实例旧串口会话 | 保留串口契约；BLE scanner 与 client/server 相互独立，扫描不能顺带停服务 |
| `src/serialforge/connection/read_thread.py` | 读取字节流，经分帧与静默间隔处理 | 原生 BLE 使用值变化事件；只有 UART 适配层才需要流式重组 |
| `src/serialforge/connection/command_dispatcher.py` | Spec 请求/响应匹配与排队 | 仅对选定 UART 通道复用；GATT read/write 的 ATT 结果独立建模 |
| `src/serialforge/spec.py:Spec` | 不可变、保留声明身份，面向命令/事件 | 保留身份约束；新 GATT 声明独立，避免几十个 BLE 字段污染既有 Spec |
| `src/serialforge/message.py:Message` | 统一串口消息，带请求和 raw_data | 通用 BLE 事件还要设备/端点/会话/操作信息，宜新增独立结果及事件类型 |
| `SerialForge.received/raw_sent` | received 只允许非空 raw_data；raw_sent 仅 bytes | BLE 允许空值，且必须携带端点来源；使用 BLE 自己的事件契约 |
| `src/serialforge/qt_core.py` | 三种 QtCore 绑定窄适配 | 保持原职责；WinRT 依赖不穿过定义层，不增加 QtBluetooth/QtGui |
| `pyproject.toml` / `uv.lock` | 串口依赖与三个 Qt extra | 经批准新增 BLE extra、Windows 标记、兼容版本和 wheel 验证 |
| `tests/` / `scripts/ci.py` / API 快照 | 串口行为与三绑定软件验证 | 增加 BLE 契约/硬件测试；既有快照不提前修改成未交付接口 |
| `README.md` / `docs/` / `.agents/ARCHITECTURE.md` | 描述已交付串口库 | 只在实际落地后更新能力、安装选项、边界和新模块地图 |

核心区别：串口是一个流式端口；GATT 是多端点的值访问和订阅系统。为 UART 设备做一个“字节通道”可以复用命令调度，但这不能替代通用 BLE 客户端和服务端。

## 5. 建议的模块与接口边界

### 5.1 对外入口：先独立，后复用

| 候选职责/名称 | 管什么 | 生命周期 |
| --- | --- | --- |
| `BleScanner` | 一次扫描、持续扫描、过滤、设备/广播更新 | start/stop 不影响既有会话 |
| `BleClient` | 一个远端设备的 GATT 连接、发现、读写及订阅 | 一个实例管理一个连接，多个实例可并行 |
| `BleServer` | 本地服务树、请求处理、订阅者及推送 | start/stop；不等于某个远端设备连接 |
| `BleUartChannel` | 使用方指定 write/notify 端点，进行可选分帧和流适配 | 依赖一个已就绪 BLE client，先订阅后发送 |
| BLE 声明/结果/事件 | 服务树、端点引用、设备信息、操作结果和请求上下文 | 不持有公开 WinRT 对象，避免平台类型泄漏 |

名称只是设计候选，不是已确定公共 API。不增加现有顶层导出名单；新的日常入口候选放 `serialforge.ble`，进阶类型归 BLE 专属模块，异常位置与既有 errors 策略统一评审。

不建议一开始将 SerialForge 改成有串口/BLE/服务端三套分支的巨型类。若你要求统一门面，应先批准一个新的组合入口；既有串口方法和扫描断开语义仍保留。UART 复用若需要抽取共享调度协议，只抽取确实共用的 send/receive/close 能力，不能把 BLE 的 DTR/RTS 方法做成空操作。

### 5.2 候选模块布局

| 位置 | 职责 | 依赖方向 |
| --- | --- | --- |
| `ble/models.py`、`ble/enums.py` | 纯 BLE 数据、能力、状态和声明 | 标准库及纯定义层；不得导入 WinRT |
| `ble/protocols.py` | 按扫描/客户端/服务端划分后端协议 | 依赖纯模型，不依赖具体后端 |
| `ble/backend/` | Windows WinRT 对象、事件令牌、COM、结果转换 | 实现定义层协议 |
| `ble/scanner.py`、`ble/client.py`、`ble/server.py` | QtCore 门面及操作编排 | 组合后端，向应用投递结果 |
| `ble/uart_channel.py` | 明确设备约定下的字节通道适配 | 通过公开会话/通道接口组合，不 deep-import 另一门面内部实现 |
| `tests/support/` | FakeBleBackend 等测试替身 | 只服务于 tests/examples，不进入发布 wheel |
| `examples/` | 自定义服务、读写/订阅、双角色、UART 桥接 | 声明具体示例 UUID 与设备业务，不进入 src |

实施时遵循现有单向依赖和绝对导入。无需先把整个串口包迁移为一个全新架构；定义层不得反向导入门面，scanner/client/server 之间通过上层组合协作。

### 5.3 必须先定的结果与事件契约

1. 端点引用带设备/服务实例/特征实例/会话世代。UUID 可重复；会话失效后旧端点必须明确报错。
2. 操作结果区分读取值、带响应写完成、无响应写被本地接受、订阅配置成功、推送结果及业务命令结果。
3. 原生 BLE 成功结果允许空 bytes；扫描结果、订阅变化、服务状态走明确事件类型，不伪造 RX 字节。
4. 若采用既有闭包习惯，默认仍仅对成功且期限内的完成投递主线程闭包；失败/取消/超时从调用对象读取。BLE 是否另加失败事件需要你批准，不默默改变原契约。
5. 连接/配对/服务发现/单次 GATT 操作分别配置期限，不能把串口发送默认 3 秒直接复制给所有 BLE 操作。
6. 日志仍为 loguru DEBUG、默认静默；发送事件注明 write/notify/indicate、设备及端点，不能把“OS 已接受”标成“对端业务已处理”。

服务端 ReadRequested/WriteRequested 是需要回复的请求，不是单纯成功通知，不能套用“超时不回调”就无人收尾。它需要独立的请求应答对象：至多一次应答、明确期限、异常/超时拒绝、deferral 完成；业务处理运行在哪个线程必须显式约定。[GattReadRequest](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattreadrequest)、[GattWriteRequest](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattwriterequest)

### 5.4 并发与资源策略

优先采用工作线程所属的 QObject 管理会话状态。WinRT 完成回调/事件可能来自非 Qt 线程，必须先经 QtCore 队列交回所属线程；用户观察事件与成功闭包再投递主线程。关闭期间仍要处理必要的取消和 deferral 完成，不能先停事件循环再等回调。

同一设备的冲突 GATT 操作进入有限队列；不同设备可并行。通知流不等待一个 UI 闭包逐条处理；过载要显式报错或按用户选择的有损策略限流。服务器对不同订阅者分别判断长度和结果。

每次连接/重建服务分配内部世代标识；迟到请求、通知、完成回调不得进入新会话。关闭要撤销 token、停止广播、拒绝或完成未决请求、取消未决操作、释放引用、退出工作线程；阶段失败也必须走同一回收路径。

COM 初始化/反初始化发生在实际使用后端的线程；不能在导入库时修改宿主全局 threading/COM 设置。STA/MTA 处理方式和等待时 GIL 行为列为原型验证项。[PyWinRT runtime](https://pywinrt.readthedocs.io/en/stable/api/runtime.html)、[Bleak Windows apartment 问题说明](https://bleak.readthedocs.io/en/stable/troubleshooting.html)

### 7.2 首轮真机矩阵建议

| 轴 | 建议覆盖 | 验收记录要求 |
| --- | --- | --- |
| Windows | Win10 22H2 与一个明确构建号的 Win11 | 不笼统写“Windows 全版本通过” |

## 8. 主要风险与处理顺序

| 风险 | 为什么影响范围 | 处理方式 |
| --- | --- | --- |
| 外设角色硬件缺失 | 直接阻断本机开服务 | B1 第一项探测；明确不支持，不用虚拟成功替代 |
| 未打包宿主权限/身份限制 | 影响库能否在普通 Python 与下游 EXE 使用 | B1 直接在目标宿主验证；分能力记录部署前提 |
| COM/回调线程/GIL | 可能卡死、无法取消或退出挂起 | 完成回调优先；验证 MTA、超时、关闭和主线程投递 |
| 同适配器双角色与广播资源竞争 | 单独角色成功不代表并行稳定 | 独立长期互通测试，能力为 unknown 时不宣称支持 |
| 广播/名字/适配器选择不可自由控制 | 用户可能期望与嵌入式协议栈相同 | 只暴露已验证能力；不提供必然成功的配置参数 |
| 缓存/随机地址/重复 UUID | 连接错设备或写错端点 | 完整端点定位、重新发现、会话世代及稳定身份策略 |
| MTU/截断/无响应写积压 | 数据损坏或伪成功 | 按实际上限校验、有限队列、显式分片协议及真实结果语义 |
| GATT 声明与原 Spec 混杂 | 原有简单 API 变复杂并出现契约冲突 | 分离 GATT 模型，仅 UART 场景复用命令层 |
| 服务停止与系统持有对象 | 停广播不代表远端立即失去已有服务/连接 | 定义本库关闭保证，验证迟到请求与远端可见性 |
| 版本/wheel 不一致 | 部分 Python 或下游打包不可用 | uv 兼容版本解析和逐 ABI 构建验证，锁定可复现组合 |
