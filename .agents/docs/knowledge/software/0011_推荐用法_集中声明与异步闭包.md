# 0011_推荐用法_集中声明与异步闭包

> 分类: knowledge/software  |  创建: 2026-10-13  |  适用范围: 使用方接入（GUI / 脚本）、README 与 docs/ 站点示例口径
> 关键词: 集中声明, send_async, add_done_callback, 闭包改界面, Message 类型注解, scan_sync, scan_async, connect_sync, connect_async, 最佳实践

## 结论（先给做法，再讲原理）

用户 2026-10-13 指定以下三步为 serialforge 期望的最佳使用方法，README、`docs/` 站点与
后续示例一律以此为主线，不再是“先 configure、再 connect_sync("COM11")、send_sync 取结果”：

1. **声明集中一处**：构造完 `SerialForge()` 后立刻把所有命令 `add(...)` 出来存成属性，每个命令只创建一次。
2. **发送与消费写在同一个函数里**：`send_async(SPEC).add_done_callback(闭包)`，闭包直接改控件。
3. **扫描即配置、连接用扫描结果**：`scan_sync(baudrates=[...], probe=SPEC)` → `connect_sync(devices[0])`。

```python
class MainWindow(QWidget):
    def __init__(self):
        # ... 先建 QApplication 与控件，再建门面 ...
        self.forge = SerialForge()

        # ① 声明集中一处：加命令只改这一段，运行时只引用对象
        self.VERSION = self.forge.add(
            request=">SN_INFO_GET=?",                          # 不用自己写 CRLF
            pattern=r">SN_INFO_GET=(?!\?)(?P<sn>.+)",          # 负向预查排除回显
        )
        self.BAUD_RATE = self.forge.add(
            request=">BAUD_RATE_GET=?",
            pattern=r">BAUD_RATE_GET=(?!\?)(?P<baud>\d+)",
            result_type=int,                                   # data 是 [921600]
        )

    # ② 发送 + 闭包在同一函数内，闭包捕获控件
    def on_get_baud_rate(self):
        def on_done(message: Message[int]) -> None:
            self.baud_panel.output.setText(str(message.data))

        self.forge.send_async(self.BAUD_RATE).add_done_callback(on_done)

    # ③ 波特率 + 探针一次给全，用返回值连接
    def on_connect_device(self):
        devices = self.forge.scan_sync(baudrates=[921600], probe=self.VERSION)
        if not devices:
            self.status_label.setText("连接状态: 未连接")
            return
        self.forge.connect_sync(devices[0])
        self.status_label.setText("连接状态: 已连接")
```

## 背景

- 真机 demo `temp/0005真机测试/U987demo2.py` 是用户认可的目标形态；此前文档把 `configure()` 与
  `connect_sync("COM11")` 当主线，声明散落在发送处，GUI 里还要自己拆线程、加定时器才能取到值。
- 集中声明 + 主线程闭包 + 扫描返回值的写法，把“协议知识”“异步结果”“设备发现”三件事各归一处，
  是这个库真正的使用体验优势，必须在文档第一屏体现。

## 细节

### 为什么声明要集中、只创建一次

- `add()` 返回的就是传入/新建的那个声明对象；声明 `frozen=True, eq=False`，注册、发送、结果全程保留身份。
  集中声明后可在回调里用 `message.spec is self.BAUD_RATE` 分发，不必按字符串或 name 找命令。
- 字段形式 `add(request, pattern, ...)` 只在声明处构造一次；不要在发送函数里重复 `add`（同一 request 重复注册会
  抛 `CommandError`，不同对象冲突同样报错）。
- 声明区也是唯一需要对照协议文档的地方：命令表和代码骨架一一对应。

### 为什么闭包能直接改界面

- `add_done_callback(callback)` 的回调统一排队到 Qt 应用主线程，闭包可安全捕获控件、局部变量；保持事件循环即可。
- 默认期限 `timeout_s=3.0`，从提交开始计时，包含排队、设备等待和主线程投递；**超时或失败不调用成功回调**
  ——需要一个“失败提示”，要么用 `call.result()`（会重抛 `serialforge.errors` 里的异常），要么像 demo 的
  `RESET` 那样用 `QTimer.singleShot` 兜底。
- 命令自身的协议预算要小于调用期限：demo 中 `RESET` 声明 `total_timeout_s=5.0`，调用处给 `timeout_s=6.0`；
  反过来会本地先超时，永远等不到多行收齐。
- 界面关闭时对未完成调用 `cancel()`，释放排队中的闭包。

### 回调参数怎么标注类型

`Message` 是 `Generic[T]`（`src/serialforge/message.py`），`add_done_callback` 的签名是
`Callable[[Message[T]], None]`，所以回调直接写 `message: Message[...]` 即可，**类型参数按该命令的解析结果填**，
和声明处的 `result_type`/`mode` 对应：

| 声明 | 回调注解 | 闭包里 `message.data` |
| --- | --- | --- |
| `add(request, pattern)`（默认 `result_type=str`，SINGLE） | `Message[str]` | 只有一个元素的文本列表 |
| `add(..., result_type=int)` / `float` | `Message[int]` / `Message[float]` | 只有一个元素的数值列表 |
| `add(..., result_type=dict)` | `Message[dict[str, str]]` | 只有一个元素的命名组字典列表 |
| `add(..., result_type=你的 dataclass)` | `Message[你的 dataclass]` | 只有一个元素的数据类列表 |
| `mode=ResponseMode.MULTI, count=N` | `Message[str]` | 收到的行列表（不足 N 行也会给出终态） |
| 一个回调服务多条命令 / `received` | `Message[Any]` | 各自解析值，用 `message.spec` 分支 |

- 直接下标即可，不需要 `from __future__ import annotations`；返回类型一并写 `-> None`。
- **类型参数仍是声明的 `result_type`，而 `Message.data` 始终是 `list[T]`**：SINGLE 的标量会在
  `Message` 边界包装成单元素列表，MULTI 保留完整列表，无回复使用空列表。因此回调统一写
  `Message[str]`、`Message[int]` 等，直接读取 `message.data`，不需要再做 `isinstance` 收窄。
- 类型参数只是给阅读者和类型检查器的信息；列表元素保持声明的解析类型，运行时不会递归复制业务对象。
- 每个调用独立：同一声明并发发送时回调类型相同，用 `message.context` 区分是哪一次调用。
- 验证方式（2026-10-13 实测，`uv run ty check <文件>`）：`Message[str]`、`Message[int]`、
  `Message[dict[str, str]]` 的 `data` 分别收窄为 `list[str]`、`list[int]`、
  `list[dict[str, str]]`。

### 为什么 scan_sync 直接接波特率和命令

- `scan_sync(baudrates=[...], probe=SPEC)` 自带完整配置，不必先 `configure()`；返回 `list[DeviceInfo]`，无匹配为 `[]`。
- `probe` 用已声明对象时直接保留原对象（不复制），且必须满足：无占位符、`SINGLE`、pattern **不能 fullmatch 自己的
  request**，否则 `DeviceProfile.__post_init__` 抛 `ConfigError: probe pattern must not match its request`
  ——demo 用 `(?!\?)` 排除回显正是为此。
- `connect_sync(devices[0])`：带 baudrate 的 `DeviceInfo` 直接按已确认波特率打开，跳过重新探测；传端口名会绕过
  VID/PID 过滤但仍要探测；无参则按保存策略发现首个设备。
- **scan_sync/connect_sync 都阻塞调用线程**：GUI 集成时改用 `scan_async()`/`connect_async()` 的闭包，
  或把它们挪到应用自己的工作线程，否则事件循环被卡住，
  闭包也投递不进来（demo 里是同步演示，注释已写明这一点）。门面不提供扫描完成或进度信号，结果只用返回值。

### 其他容易写错的地方

- request 不需要手写 CRLF：注册与发送都先 `normalise`（去掉一个结尾终止符）再补配置的 `terminator`（默认 `\r\n`），
  写不写都只发一份；接收定界由 `framing` 单独控制。
- `result_type`：默认 `str` 返回整段匹配帧；`int`/`float` 取第一个捕获组转标量（`(?P<baud>\d+)` → `921600`）；
  `dict` 返回命名组字典；`dataclass` 按命名字段构造。命名组名字要和 dataclass 字段一致。
- 多行响应：`mode=ResponseMode.MULTI, count=N`，`data` 是行列表；单行响应同样是只有一个元素的列表；`idle_timeout_s` 只是行间隔上限，
  不足 N 行会提前完成，成功与否要在闭包里自己判定（demo 用 `set(lines) == {"OK", "SYS_START", "IDLE"}`）。
- 状态回显：需要“连接状态”时用 `connection_state_changed`，或 `connect_sync()` 返回 / `connect_async()` 回调后的 `forge.state`，不要靠定时器猜。
